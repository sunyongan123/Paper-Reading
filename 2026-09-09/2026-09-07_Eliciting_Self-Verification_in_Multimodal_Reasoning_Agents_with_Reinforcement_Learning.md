## 1. 研究背景与要解决的问题

多模态大模型（MLLM）正在从"看图说话"进化为会调用工具（网页搜索、代码执行）的 Agent。但一旦涉及检索，问题就变了：搜索结果天然嘈杂，可能是过时、跑题甚至互相矛盾的网页摘要；模型需要判断"此刻到底该不该搜"、"搜什么词"、"哪条证据可信"。更麻烦的是，训练时往往只有"最终答案对不对"这一个结果级信号，中间每一步（要不要搜、信哪条）都没有标注。

作者用已有的 GRPO 微调方法 MMSearch-R1 做了定量体检，暴露三个典型病灶：(1) 该搜不搜——超 10% 用例漏掉必要搜索，反而 30% 用例做了多余搜索；(2) 检索结果约 45% 与问题无关，即使搜对了、结果里已有正确证据，仍有 28% 以上的用例答错（过度信任第一条片段、不处理冲突）；(3) 文本查询本身约 19.5% 跑题，过早带偏整个轨迹。且 GRPO 的组内相对优势在"同组奖励几乎全平"时学习信号会失效。本文要补的缺口正是：如何用纯 RL、在无外部验证器的情况下，教会紧凑模型自己校准搜索并过滤证据。

## 2. 核心方法 / 思路

作者提出 SVRL（Self-Verification via Reinforcement Learning，纯 RL 微调），把"何时搜、搜什么、信什么"全部变成可优化的轨迹级信号。整体像给 GRPO 加了几把"软尺子"，所有奖励乘在最终答案正确性上（`r=(1-α)·r_acc·r_svrl+α·r_fmt`），只有答对才给过程分，从根上防 reward hacking。

- **搜索校准（何时搜）**：训练前先让模型"无工具答一次"，答对的样本记为 search_free；RL 滚动中若这类样本还调用搜索，就乘以 0.1 的惩罚（r_aware）。这样只罚"可避免的搜索"，不误伤真需要搜的题。
- **查询多样性（搜什么）**：要求模型一次给出 5 条候选查询，随机执行 1 条；奖励里乘上"合法唯一查询占比"因子（r_count），逼模型把搜索意图写具体、写多样。
- **证据自验证（信什么）**：模型在每次工具调用后输出结构化二进制向量 `<verify> 0,1,0,1 </verify>` 配合一句自然语言理由；训练时用带真值的 GPT-5 当 oracle 给每条查询/摘要打标签，让模型的自评分（query-align 与 snippet-align）去对齐这些标签。推理时丢弃 oracle，完全靠模型自己验。
- **稳定训练**：采用 Dr. GRPO（去掉归一化项），并靠更细的奖励增大组内方差，使组大小可从 8 缩到 4，单机 8×A100 吞吐更好。作者也试过 LLM-judge 奖励，但观察到加长答案刷分的 reward hacking，故训练一律用精确匹配。

与已有方法的关键差异：MMSearch-R1 只奖励"最终对＋少搜"，SVRL 把检索过滤本身变成了可学习、可解释的动作；且不需要推理时的外部 rerank/验证模块。

## 3. 关键实验结果

在 FVQA（5,000 训练/1,800 测试）上对 Qwen2.5-VL-7B 做 RL 微调，评测 FVQA、InfoSeek（域内）与 MMSearch、LiveVQA、SimpleVQA（域外，OOD），准确率用 GPT-5 裁判。

- **主结果（自适应搜索）**：SVRL-full-7B 在 FVQA-test 达 65.3%、InfoSeek 64.7%，比最强基线 MMSearch-R1++（56.4%/55.1%）各高约 8~9 个百分点；搜索率反而降（FVQA 上 61.4% vs 80.3%）。OOD 上同样全面领先：MMSearch 60.3 vs 53.8、LiveVQA 57.8 vs 48.4、SimpleVQA 58.3 vs 57.4。作为 7B 模型，FVQA 上 65.3% 已逼近"始终检索"的 GPT-4o（66.0%）。
- **消融（Table 1）**：仅 query-align 会把搜索率拉到 97.6%（刷分）；加 search-aware 后精度到 59.9%；纯自验证（SVRL-self-verification）FVQA 64.2、InfoSeek 64.1，搜索率仅 61.2%，证明验证信号是主要增益来源。
- **工具行为分析**：搜索精确率约 89.9%→97.7%、召回约 54.6%→70.8%；自验证掩码与 GPT-5 oracle 标签一致率 71.3%，且偏差集中在"过少过滤"（保留噪声 1495 例 vs 误删有用 82 例）。
- **规模/扩展性**：同一配方换 Qwen3-VL-8B 得 64.9/64.0，超过 GPT-5.2-thinking 的 60.8/52.2；加大推理期搜索预算（最多 15 路并行、多数投票）时 SVRL 持续涨点，而基线在约 5 次搜索后饱和。

这说明：即便只做 RL、不引入外部验证器，紧凑模型也能学会"边推理边验证据"，把精度与工具开销这对矛盾一起改善。

## 4. 亮点与贡献（Why it matters）

1. **纯 RL 框架，推理零外部依赖**：验证能力被内化进轨迹，部署成本不增反降，对小模型特别友好。
2. **把"隐性反思"显式化**：`<verify>` 结构化分数让证据取舍可监督、可解释、可评测，而不是依赖自由文本批判。
3. **细粒度奖励缓解 GRPO 信号坍缩**：同组奖励方差变大，组大小减半（8→4），训练吞吐与稳定性双赢。
4. **数据效率惊艳**：仅 5,000 条 VQA 样本就换来域内外一致提升，逼近/超越大得多的闭源模型。
5. **验证出真问题**：测试时用外部 verifier 的对照实验，定量证明"证据过滤"是当前工具型 Agent 的支配性错误源。

## 5. 局限与可改进点（个人点评）

- **对带真值 oracle 的依赖只是"挪了个位置"**：推理端确实不需要外部验证器了，但训练端每个样本都要 GPT-5 在知道标准答案的前提下打标签——这条流水线的成本、时延与裁判偏差仍在，且自验证质量上限被 teacher 锁死。
- **评测口径不够自洽**：报告主指标也是 GPT-5 裁判，裁判不可复现、易被提示词扰动；作者承认 EM 下 SVRL 明显掉分（如 FVQA 65.3→43.0），说明不少"增益"依赖语义宽容的裁判。
- **行为域偏窄**：行动空间仅图像搜索/文本搜索/作答，最多 3 轮交互、上下文 8124 token；没有长程记忆、跨回合纠错，也不含点击等 GUI 类操作，离"通用多模态 Agent"还远。
- **过滤仍偏保守**：自验证倾向保留噪声而非丢弃有用证据（1495 vs 82），在对抗性/高噪声检索下可能翻车；对查询语言等工具参数敏感（SimpleVQA 增益小）。

## 6. 对我们的启示 / 可借鉴点

- "把过程信号乘在结果正确性上"是防 reward hacking 的好范本：GUI 场景做过程奖励时，也应只对"任务最终成功"的轨迹发放元素级/步骤级加分，避免模型学会刷中间分而不完成任务。
- "训练时用强验证器蒸馏、推理时零依赖"的范式，可直接用于给 GUI Agent 内置一个"轻量自评模块"，替代昂贵的真值环境。
- search_free 的"自标注"思路通用：GUI 里可用弱模型预判"这步不查也能做对"，从而区分必要的 vs 可避免的观察/工具调用。

**对 GUI Agent 的可借鉴点：** 这是本文对跨域参考最有价值的一段——多步 GUI 操作中，"观察"就相当于这里的"检索"，同样嘈杂、同样缺标注。可迁移三点：(1) 让 GUI Agent 对每一步的 UI 观察/grounding 结果输出结构化"有用性分数"（如对每个候选元素的置信掩码），并用 RL 对齐真值环境事后标注，从而把"我在屏幕上看到的东西是否可信"变成可学习能力；(2) 把"要不要再截一屏/拉一次 accessibility dump"类比为"何时搜索"，用 search-aware 式奖励惩罚可避免的额外观察，砍掉冗余步数；(3) 训练期用外部"上帝视角"（如已正确渲染的后台状态）给元素匹配打标，推理期让模型自己验——这条"验证检索到的证据"的链路正是 GUI 多步操作最容易出错、也最值得先落地的一环。
