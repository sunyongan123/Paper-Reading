## 1. 研究背景与要解决的问题

手机上的 LLM Agent 目前主流是"纯 GUI 路线"：像人一样看截图、点按滑。这套界面通用，但简单任务也常要十几步——导航进目标页、定位文本、逐字输入，又慢又脆。另一条路是工具动作（tool action）：绕过屏幕，直接经 API 或读 App 数据库完成语义操作，比如把"进便签→找到那段文字→替换"压成一次数据库写入。业界已开始把两种动作拼成混合动作空间，但工具这条路在手机上基本没人走通，卡点是**造工具太费人**：每个 App 的状态布局不同，手写工具不可持续。

更深一层，就算自动生成了工具，"怎么验证它真的可靠"也远比想象中难：用 mock 接口单测，常常在真机上一跑就崩（假阴性）；直接在模拟器上测，又摆不好前置条件——测"读数据"得先知道有没有这条记录，测"删除"得先造一条目标记录出来。本文要补的缺口：**如何以最少人力为 GUI Agent 自造可靠的工具函数，并让工具与 GUI 动作在一个动作空间里协同**。

## 2. 核心方法 / 思路

作者提出 DroidTool：把"造工具"本身交给一个 LLM agentic 工作流，产出的是**作用于应用状态（App 的 SQLite 数据库、SharedPreferences、文件、ContentProvider）的 Python 函数**，通过 ADB 在设备上执行；Agent 在每步既可以选 GUI 动作，也可以函数调用式地调用这些工具，工具返回结果进入历史上下文供后续决策。工具生成流程分五段（类似"造工具 = 微型软件开发"）：

1. **工具提案与规格**：人类专家先为每个 App 写一份 Developer Document（描述有哪些状态实体、字段、访问路径、一致性/恢复约束，不含源码），design agent 据此按"实体生命周期"（create/read/update/delete 或 get/set）提出一簇工具，specification agent 再转成结构化实现契约。人工介入只剩"写文档"这一步。
2. **工具实现**：implementation agent 把规格写成 Python 模块，每个函数带 success 标志与 error 字符串；规则检查器验语法与结构合规，不合规就重生成。
3. **测试生成与执行**：test agent 生成"输入参数 + 断言"的测试，在真实 Android 模拟器里执行。**亮点是关系化测试（relation-aware）**：不为每个工具单测，而是把操作同一状态实体的工具按依赖排成调用序列（create→read→delete），让前面的工具为后面的工具自然造好前置条件；缺少前置条件则跳过该用例，且跳过不算通过。这既提升了覆盖率，也避免了 mock 造成的假阴性。
4. **修复与注册**：测试失败的工具交给 repair agent 分析执行结果并改源码，只动有缺陷的部分，再跑旧测试，循环直到全过或达迭代上限。通过的工具注册为动作选项，供 Agent 按元数据（函数名、输入输出 schema、描述）调用。

与已有基线对比的关键差异：GUI+Skill 只是把"点按流程"写成 skill.md 让模型照着做（仍是 GUI 动作，且常牺牲安全）；GUI+CLI 给通用 shell，命令容易语法错、权限错；DroidTool 给的是**针对 App 状态、预先在真机上验证过**的语义工具。

## 3. 关键实验结果

在 AndroidWorld（AW，116 任务）、B-MoCA（BMC，用 119 任务）、MobileSafetyBench（MSB，100 个日常场景任务）上评测，共 335 任务、29 个 App，统一用 Gemini-3.5-flash。

- **主结果（Table 1）**：DroidTool 总体成功率 79.20%，比 GUI-only（74.73%）**高 4.47 个百分点**；分基准为 AW 77.30 vs 69.83、B-MoCA 82.35 vs 78.71、MSB 77.67 vs 75.67。每任务平均交互步数从 8.13 降到 6.50（**约省 20.05%**）；B-MoCA 闹钟设置等复杂任务上省了 10 步以上。对照：GUI+Skill 71.44（反而更差且降低 MSB 高危任务安全分）、GUI+CLI 77.01（CLI 命令成功率仅 83.77%，573/684）。
- **验证策略消融（Table 2/3）**：Relation 从 121 个提案工具中注册 113 个，远超 Unit（101）与 Separate（82）；下游工具调用成功率 90.20%（Unit 74.86%、Separate 78.76%、Unverified 仅 73.41%）；基准成功率 79.20% vs 78.61%（Unit）/76.22%（Separate）。未验证工具（Unverified）整体 74.03%，说明"不过滤可用、乱过滤伤能力"——mock 单测曾把 Joplin 一个其实好用的 search_notes 工具误杀。
- **工具实际效用**：工具对"重复性状态操作"（改笔记、建日历事件、改应用设置）收益最大；安全类任务里 Agent 能用工具快速核查短信等上下文（判断是否涉非法活动），提升效率的同时保住安全。

结论非常直接：自生成、且经关系化真机验证的工具，能同时买到"更会做"与"更省步"。

## 4. 亮点与贡献（Why it matters）

1. **打通"自动造工具→验证→嵌入混合动作空间"全链路**：把人工成本从"逐个写工具"降到"每 App 写一份状态文档"，这是工程上真正可规模化的一步。
2. **关系化验证是方法论亮点**：让测试工具互为前置条件（create 供 read/delete 用），巧妙解决真机测试摆前置条件的死结，同时把覆盖率与可靠性一起提上去，还避免 mock 假阴性误杀好工具。
3. **实证价值扎实**：三个代表性基准、统一主模型、三种验证策略 + 未验证对照齐全，量化了"验证设计不当反而更糟"这一反直觉结论。
4. **为"效率型 GUI Agent"提供新杠杆**：混合动作空间下，Agent 可自由决定"这步该点屏还是调工具"，是迈向低成本、长任务手机 Agent 的实用解法。
5. **结果可复用**：工具一经验证即为持久资产，可在多任务间摊薄生成成本（作者在 Limitation 中也指出这点）。

## 5. 局限与可改进点（个人点评）

- **Developer Document 仍是人工瓶颈**：每个新 App 都要人写状态文档，App 版本升级后文档与状态还可能漂移；作者自己也承认自动编档是下一步。这意味着"无需源码"的宣称其实把成本转移给了文档维护。
- **工具静态、离线生成**：工具在任务执行前一次生成完毕，运行中不能按需新增/裁剪/修复；对长尾或动态需求（新装 App、临时功能）无力。
- **验证只覆盖"函数执行不报错"**：工具调用成功率高不等于任务结果正确——工具改了状态但 UI 呈现错误这类"副作用错"没有被直接测试；作者亦承认 GUI 层面校验缺位。
- **对单一闭源模型依赖**：全部结果建立在 Gemini-3.5-flash 上，工具生成质量与 Agent 决策质量耦合，换个基座未必同增益；也未见成本对比（API 消耗、修复迭代轮数）。
- **评测安全维度的交代较粗**：MSB 上工具既用于"高效完成"也涉及敏感操作核查，但缺少对工具滥用边界（least-privilege、用户授权）的机制讨论。

## 6. 对我们的启示 / 可借鉴点

- "先写状态文档、再生成工具"的中间层思想可直接借鉴：与其让 GUI Agent 去猜数据库 schema，不如给一套紧凑的、人可维护的"状态接口清单"，让 grounding 与工具调用都建立在这层可信接口上。
- "关系化验证"非常值得移植到我们的评测/回归体系：当项目里有多个互相依赖的能力模块（如取元素→点击→断言状态变化）时，把它们的验证串成前置条件链，比逐个单测更接近真实使用、也更难造假。
- 对"效率导向"的 Agent 优化目标（如减少交互步数、减少截图/OCR 调用）而言，这篇提供了把工具动作当作"可被学习选择的捷径"的清晰框架——这正好可作为后续用 RL 在 GUI+工具混合动作空间里学习"何时切捷径"的训练环境。
