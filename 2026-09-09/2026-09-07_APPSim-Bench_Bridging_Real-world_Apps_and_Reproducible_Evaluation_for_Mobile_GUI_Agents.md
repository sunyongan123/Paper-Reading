## 2. 论文要解决的核心问题

- **要解决的问题**：如何对移动 GUI 智能体做一次"既真实、又可复现、还能自动打分"的系统评测。
- **为什么重要**：移动 GUI Agent 是 VLM 落地 HCI 的核心方向，但评测环境的不稳定直接决定模型排名是否可信——环境噪声会污染所有对比结论。
- **现有方法的不足**（论文明确批评的三类）：
  1. **静态 trace 评测**（如早期截图/演示基准）：靠"动作序列是否匹配人工黄金路径"判成败，遇真实 App 的**多路径问题**会误杀合法操作（如换条路完成下单被判失败）。
  2. **动态系统/开源 App 评测**（AndroidWorld 等）：虽从"路径比对"转向"结果验证"，但只覆盖系统或开源 App，与日常第三方服务差距大。
  3. **真机跑商业 App**（SPA-BENCH、LlamaTouch）：够真实，但推荐算法、广告位、账号状态、动态内容（Fig.1a 搜索建议/购物车状态跨环境漂移）导致同一任务在不同时间/设备呈现不同状态，**违背基准设计的基本可复现原则**。
- **Research Gap**：作者认为已有工作一直在"真实 vs 可复现"之间二选一，缺乏一个"通用、高效、二者兼得"的方案（Table 1 中 AppSim-Bench 是唯一同时满足第三方 App、可复现、自动化、低噪声的行）。

## 3. 方法核心思想（三层拆解）

### 3.1 一句话概括方法

把真实高频交互搬进"可控可重置"的模拟 App，用**结果验证**替代路径比对，实现确定性评测。

### 3.2 方法总览（Pipeline）

基准由三层构成，数据流为「任务指令 → 模拟 App 交互 → 状态检查判分」：

1. **任务层（Tasks）**：15 名志愿者产出真实交互，人工标准化为自然语言任务；共 557 个、17 个 App（中文 9 App/283 任务，英文 8 App/274 任务）。按参考步数分三档：≤5 步 282、6–10 步 140、≥11 步 135；另设 183 个数值推理子集（计数 65 / 算术 45 / 比较 75 / 阈值过滤 21，非互斥）。
2. **模拟 App 层（Simulated Apps）**：人主导、编码 Agent 辅助——人给任务需求/后端 schema/页面层级/任务路径截图，Agent 生成候选实现，人检查、执行、迭代纠错；只保留任务相关页面，用可控后端替换真实服务，从确定初始状态启动、可重置，剔除个性化/广告/网络/动态内容等随机源，运行于**原生 Android**。
3. **自动化评测层（Automated Evaluation）**：沿用 AndroidWorld 的结果验证，任务结束后检查"可见或后端状态是否达成目标"，分 **State**（消息已发/订单已下）、**Answer**（返回数量/价格等结构化答案）、**Hybrid**（两者兼有）三类，用确定性判分。

### 3.3 真正的创新点（去伪存真）

- **真·方法创新**：三层分离（规格 / 参考执行 / 官方打分）以支持确定性判分；"高频真实任务 + 可控后端 + 结果验证"的组合在移动 GUI 评测中尚属首次，且**双语生态**（中英 17 App）是独有覆盖。
- **工程组合**：结果验证（AndroidWorld）、模拟 App（AppWorld 思路）均为已有组件，本文把"仿真环境"从 API/代码范式移植到**像素级 GUI 范式**，是对已有理念的工程复用与重定位。
- **对性能（可信度）最关键的设计**：**可控后端数据 + 确定性结果验证**是去除环境噪声、保证可复现的核心；剪枝残余上界仅 ≤4.28%，证明剪枝不是捷径。
- **证据不足 / 仅声称有效**：行为保真度是"间接测量"（placeholder 残余而非直接覆盖率），构造质量靠"人工多轮检查"而非标准化的 inter-annotator agreement 或 bug rate，作者在 Limitations 中自认证据有界。

## 4. 具体技术细节

### 4.1 模型结构

本文**不训练任何模型**。被评测的是 19 个现成智能体：15 个通用模型（GPT-5.5/5.4/5、Claude-Opus-4.7/Sonnet-4.6/Sonnet-4.5/Haiku-4.5、Gemini-3.1/3/2.5-Pro、Qwen-3.6-Plus/Flash、Doubao-Seed-2.0/1.8/1.6）+ 4 个 GUI 特化模型（MobileAgent-v3.5、UI-TARS-1.5-7B、AgentCPM-GUI、V-Droid）。Qwen/Doubao 用官方 GUI prompt，Claude/GPT/Gemini 用单模型版 M3A 适配（去掉多 agent，仅保留移动观测 + Set-of-Mark 定位 + 动作历史）。

### 4.2 训练流程（若需要训练）

无训练。这是纯评测基准，方法全部落在"环境构造 + 评测协议"上。

### 4.3 推理流程（评测协议）

- **单步循环**（ReAct 式）：每步 agent 收到「任务指令 + 当前截图（含 Set-of-Mark 标注）+ 文本动作历史」，输出一个动作；动作空间为像素级原语 tap/swipe/type/scroll/open_app/answer/status 等。
- **协议**：Android 13（API 33）、分辨率 1080×1920、temperature=0、每任务 50 步上限；任务开始前清状态、恢复任务初始态、重置历史。
- **终止与判分**：`status(complete/infeasible)` 或达到 50 步预算即止；二元 ACC 判分（达成目标=1，否则=0），Answer/Hybrid 的答案抽取经人工审计无错。

## 5. Benchmark 与实验设置

### 5.1 Benchmark 一览表

| Benchmark | GUI 场景 | 任务类型 | 数据规模 | 输入格式 | 输出格式 | 评测指标 |
|---|---|---|---|---|---|---|
| **AppSim-Bench（本文）** | Mobile（模拟 App，原生 Android） | 端到端多步任务（State/Answer/Hybrid）+ 数值推理 | 557 任务 / 17 App / 双语 | 截图 + 指令 + 动作历史 | 动作序列 / 结构化答案 | 二元 ACC、AvgAct、ActOH |

对比定位（Table 1）：AndroidWorld 116 任务/20 App（仅系统/开源）、SPA-BENCH 340/68（真机、不可复现）、LlamaTouch 496/57（真机、不可复现）；AppSim-Bench 557/17，每 App 均任务数 32.8 最高，且唯一"第三方 App + 可复现 + 自动化 + 低噪声"全满足。

### 5.2 实验结果分析

**主结果**（19 agent，同协议）：

- **天花板极低**：最强 Claude-Opus-4.7 仅 **50.27%**，Gemini-3-Pro 49.91%、GPT-5.5 49.73%、Gemini-3.1-Pro 49.55%，头部全在 50% 下方；第二梯队骤降（GPT-5 33.39%、Gemini-2.5-Pro 17.24%）。
- **GUI 特化未补差**：最强 MobileAgent-v3.5 31.42%，其余 <23%（UI-TARS-1.5-7B 22.62%、AgentCPM-GUI 10.05%、V-Droid 9.87%），说明瓶颈在任务本身而非缺 GUI 后训练。
- **系统性盲区**：**28.55%（159/557）任务无任何模型解出**，仅 0.36%（2 个）被全部 19 家解出——失败是共享的能力缺口，而非模型间排序差异。
- **生态鸿沟**：头部模型中文 App 约 59–60%，英文掉到 39–41%。
- **越长越差**：所有模型随参考步数单调降（GPT-5 43.62%→31.43%→14.07%）；≥11 步档最强仅 33.33%（Gemini-3-Pro），特化模型近乎归零（AgentCPM-GUI 0.00%、V-Droid 0.74%）。
- **数值推理败在"推理"而非"读"**：算术 GPT-5.5 最高 57.78%；阈值过滤最难，Opus-4.7 的 42.86% 已居首，多数 <15%。人工审计 1,287 步仅 1 处感知/抽取错（0.08%），失败几乎全在推理阶段。

**Ablation / 质量验证**（benchmark 无模型消融，用"可信度验证"替代）：

- **剪枝残余上界 ≤4.28%**：把模拟 App 中被剪枝的真实页面状态补回（悲观上界），成功率的偏移最多几个百分点，证明剪枝非可被利用的捷径。
- **视觉保真盲评**（7 人 / 11 场 / A/B）：静态截图 46.3% 判"无法区分"、19.0% 认假为真；动态序列 35.7% 无法区分、15.2% 认假为真——环境"视觉上不易辨伪"。
- **效率-准确率负相关**（Fig.5）：ACC 与 AvgAct Pearson −0.669、与 ActOH −0.458、与预算耗尽数 −0.705；预算耗尽轨迹共 2,036 条，成功率仅 0.44%，其中 83.01% 含 ≥3 次连续重复动作——低分并非单点失败，而是"原地打转"的低效执行。

## 6. 亮点与贡献（Why it matters）

1. 首次在移动 GUI 评测中把"真实（第三方高频 App）"与"可复现（可控后端 + 确定性验证）"系统性统一，补上领域长期缺口。
2. 双语生态（中英 17 App、557 任务）与专门数值推理子集，覆盖比 AndroidWorld/SPA-BENCH 更广的日常场景。
3. 构造流程可复制：spec → 编码 Agent 生成 → 人工校验 → 仪器化，摊薄人工、易扩展新 App/生态。
4. 19 个通用/特化模型同协议大横评，把共同短板精确定位到三类能力：长程状态追踪、界面上数值约束、卡壳恢复。
5. 质量证据链较完整：视觉盲评 + 剪枝上界 + 错误分解三重证据，增强基准可信度。

## 7. 局限与可改进点（个人点评）

- **仿真是"有损温室"**：剥离广告/个性化/网络/账号/长尾数据，测的是理想界面下的确定性执行，无法外推到真实部署的抗扰能力（论文自认）。
- **构造质量证据偏软**：缺标准化的 inter-annotator agreement 与残余 bug rate，行为保真用"间接上界"而非直接覆盖率度量；错误分解只深审单个 App（JD），跨生态未确认。
- **协议偏单一**：temperature=0 + 单次运行，未报告运行方差；50 步"预算耗尽"当失败代理，对状态变化下的合法重复动作偏保守（作者也提醒重复≠循环）。
- **规模 vs 长尾**：每 App 平均约 33 任务，跨 App 长流程、实时交互、无障碍、安全敏感场景均未覆盖。
- **生态偏差未解**：中英 60% vs 40% 的落差究竟是语言、训练数据还是 App 难度所致，未做归因。

## 8. 对我们的启示 / 可借鉴点

- **评测工程范本**：高频真实场景搬进可控环境 + 结果验证 + 三层分离，可直接复刻；其对随机源（推荐/广告/账号/动态内容）的**清单化管理**尤其值得抄进自家评测规范。
- **给 Online RL 的廉价信号**：ACC 与动作开销、预算耗尽、连续重复强负相关（−0.669 / −0.705），这些免标注轨迹统计可直接作 reward shaping 或"死循环终止/恢复"检测特征。
- **造环境流水线可迁移**："人给规格、编码 Agent 生成、人校验"可低成本扩展新 App/生态，产出沙盒本身就是 SFT/RL 的现成环境。
- **能力短板即研究方向**：长程状态追踪、界面阈值过滤式数值约束、卡壳恢复是 19 家共同盲点，正对 RL 与长程建模的落点。
- **评测须分层报告**：中英生态精度差异提示按语言/平台分组报告，避免混合均值误导结论。
