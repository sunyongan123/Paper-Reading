# SRPO: Setwise Relative Policy Optimization for Multi-Agent LLMs

> 一句话 TL;DR：把共同触发一次环境状态迁移的多个智能体输出打包为 active set，用基数归一化 + 单次裁剪的相对策略优化统一分工、共演与动态路由三类工作流。

## 2. 论文要解决的核心问题

- **要解决什么问题**：多智能体 LLM 系统用端到端 RL 训练时，**"策略优化的更新单元"到底该是什么**？属于通用 Agent / MAS 场景，不限于 GUI。
- **为什么重要**：RL 的一切（credit assignment、优势估计、裁剪、梯度）都建立在"一个动作"的定义之上。如果动作边界划错，同一决策会收到不一致的更新，训练信号被污染，团队级协作无法稳定收敛。
- **现有方法有什么不足**：MAGRPO、Stronger-MAS、Dr. MAS 等 MAS-RL 方法都**按协作流程的组织方式来切分更新单元**——按角色/轮次（分工范式）或按并行组别（联合共演范式）分组。其结构性缺陷是：agent 身份、执行顺序、rollout 布局决定了优化器"看到的动作"，而非环境真实发生的那次状态迁移。作者明确指出后果——"当参与输出的智能体数量或顺序改变时，同一环境决策会收到不同的更新"。
- **Research Gap**（作者视角的 claim）：缺乏一个**与 agent 身份、顺序、编排方式解耦**的 MAS 动作定义，使分工、联合共演、混合/动态路由能共用同一条优化规则。

## 3. 方法核心思想（三层拆解）

### 3.1 一句话概括方法

把"一次环境状态迁移实际消费掉的那组新采样输出"定义为 **active set（活动集合）**，当作一个**集合级动作**做相对策略优化。

### 3.2 方法总览（Pipeline）

- **输入**：共享的 pre-action 状态（任务 + 交互历史 + 编排内存）；**输出**：一次环境迁移 + 团队奖励。
- **模块链**：路由器 μ_ϕ 激活一个策略子集 → 被选中的 worker 策略 {π_θi} 从同一 pre-action 状态**并行采样**输出 → 环境/聚合器 α_ψ 消费这一整组输出触发状态迁移 → 得到团队回报 R_e。
- **优化侧四步**：① 识别完整事件（同一 pre-action 状态采样、被同一次迁移消费的集合，基数 K_e）；② 成员 log-ratio 求和后做 **1/√K_e 基数归一化**，得到集合比率 ρ_e；③ 给整个事件分配**一个**组间相对优势 Â_e；④ 对整个集合**裁剪一次**、按事件（而非 token/成员行）求平均。
- **关键抽象**：K_e=1 是分工（singleton），K_e>1 是联合共演，K_e 随事件变化即混合/动态路由——三者是同一公式的不同基数。

### 3.3 真正的创新点（去伪存真）

- **真·方法创新**：① active set 作为**工作流无关的动作表示**（此前无人以"环境迁移边界"定义 MAS 动作）；② 1/√K_e 基数归一化的集合比率——用方差分解（Var = σ²_e + 2/K_e·Σ Cov）说明独立成员时单成员尺度**精确保持**、相关成员显式进入第二项，是公式上站得住的原创。
- **工程组合**：组间相对优势、PPO 式裁剪、事件原子批处理、缺失成员废弃等，均为 GRPO/PPO 已有组件，本身不新，但组合有效。
- **对性能提升最关键的设计**：**√K 归一化**（搜索消融中比 1/K 均值高 +5.4/+7.5 点）+ **事件级归约**（梯度范数 CV 0.107 < token 级 0.142）。
- **证据不足 / 仅声称有效**：固定算力预算下的优势作者自己承认"尚待证明"；K 只消融了 1 和 5，未系统扫描 2/3/4。

## 4. 具体技术细节

### 4.1 模型结构

纯 **LLM**（非 MLLM，无视觉编码器），多策略集合：worker 策略 {π_θi} + 路由器 μ_ϕ + 聚合器 α_ψ（三者可共享或独立参数）。Base model：数学任务 **Qwen3-4B / 8B**，搜索任务 **Qwen2.5-3B / 7B**。整体是 GRPO 系在线 RL 后训练，非冻结、可微调。

### 4.2 训练流程（SRPO loss 设计是重点）

| 阶段 | 目标 | 训练什么能力 | 数据来源 | 数据形态 | 训练目标 / Loss |
|---|---|---|---|---|---|
| 在线 RL 后训练（无独立 SFT） | 端到端优化整支队伍的协作策略 | 分工、联合共演、动态路由（可变 K_e） | 数学：处理后的 DAPO-Math 子集；搜索：处理后的 HotpotQA 子集 | 文本轨迹：事件 ID + 前状态 ID + 成员索引 + 策略版本 + 旧 log-prob | SRPO 集合式相对策略目标（下详） |

**SRPO loss 的四段式设计**（相对标准 GRPO 仅增三步）：

1. **成员 log-ratio**：对事件 e 内成员 j 计算掩码后的序列级 log-ratio ℓ_{e,j} = Σ_u m_{e,j,u}·log(q_cur/q_old)，掩码去掉 prompt/padding/环境 token。
2. **基数归一化集合比率**（核心）：L^set_e = (1/√K_e)·Σ_{j∈S_e} ℓ_{e,j}，ρ_e = exp(L^set_e)。设计动机：若成员独立，Σ 的方差是 K_e·σ²，除以 √K_e 后**恰好回到单成员尺度**，避免"集合越大更新步长越大"的系统偏差；若成员相关，相关项显式保留而非被错误消掉。
3. **单优势**：Â_e = (R_e − μ_{g(e)}) / (σ_{g(e)} + ε)，按"可比 prompt + 事件类型"分组做组内标准化，全体成员共享同一标量。
4. **单次裁剪 + 事件级平均**：J_SRPO = (1/|B|)·Σ_e min(ρ_e·Â_e, clip(ρ_e, 1−ε, 1+ε)·Â_e)。**按事件而非 token/成员求平均**，保证每个环境迁移只贡献一次更新。

**实现约束**：同一事件的行必须同进一个 mini-batch（事件原子批处理）；缺失成员则**废弃整个事件**而非静默改动作。这是新增的唯一系统工程要求，rollout、奖励、优势估计、优化器均可照旧替换。

### 4.3 推理流程

**多步推理**，ReAct 风格循环：路由器读观测 → 决定激活子集（`<route>1,3</route>` 或 `<route>STOP</route>`）→ 成员并行采样 → 环境/工具执行（搜索任务接检索引擎）→ 校验器判断证据是否充分 → 循环，直至路由器 STOP + 聚合器输出最终答案，或达 max_turns。数学任务为 solver–verifier 循环，搜索任务为 router–search–verify 循环。

## 5. Benchmark 与实验设置

### 5.1 Benchmark 一览表

| Benchmark | GUI 场景 | 任务类型 | 数据规模 | 输入格式 | 输出格式 | 评测指标 |
|---|---|---|---|---|---|---|
| AIME'24 / AIME'25 | General | 数学推理（竞赛） | 公开集（各 30 题级） | 纯文本问题 | `\boxed{}` 答案 | Avg@16 / Pass@16 |
| AMC'23 | General | 数学推理 | 公开集 | 纯文本 | `\boxed{}` | Avg@16 / Pass@16 |
| MATH500 | General | 数学推理 | 公开集（500 题） | 纯文本 | `\boxed{}` | Avg@16 / Pass@16 |
| Minerva / OlympiadBench | General | 数学推理 | 公开集 | 纯文本 | `\boxed{}` | Avg@16 / Pass@16 |
| NQ / TriviaQA / PopQA | General | 单跳检索 QA | 公开集 | 纯文本 + 检索文档 | `<answer>` | Avg@16 / Pass@16 |
| HotpotQA / 2Wiki / MuSiQue / Bamboogle | General | 多跳检索 QA | 公开集 | 纯文本 + 检索文档 | `<answer>` | Avg@16 / Pass@16 |

评测统一每查询采样 16 条（Avg@16=平均正确率，Pass@16=至少一条正确），宏平均为展示 benchmark 的未加权均值。

### 5.2 实验结果分析

- **主结果（数学，Qwen3-4B/8B）**：SRPO 4B 达 macro Avg@16=**61.3±0.5**、Pass@16=**77.9±0.8**；8B 达 **62.5±0.5** / **77.8±0.7**。两个规模均以 **0.2 点**超过展示的最强 Dr. MAS 行，但单数据集增益不均（AIME 类最硬、MATH500/AMC 较易）。
- **主结果（搜索，Qwen2.5-3B/7B）**：3B 达 **40.1±0.5** / **56.1±0.8**，7B 达 **45.6±0.4** / **61.6±0.7**。相对最强 Dr. MAS 行，3B 提升 **+3.2/+3.1** 点、7B 提升 **+1.8/+3.3** 点，是增益最大的场景。
- **Ablation（搜索，Qwen2.5-3B）**：① 基数：K=1 单例 37.2/52.4 → K=5 的 SRPO 40.1/56.1（**+2.9/+3.7** 点），证明集合动作收益；② 归约：K=5 下未归一化求和 38.6/54.3、1/K 均值 34.7/48.6，**√K 全面占优**（比均值高 **+5.4/+7.5** 点），证明归一化方式最关键。
- **训练动力学**：事件归约 8B 运行的梯度范数稳定在 **[56.97, 108.10]**、CV **0.107**（低于 token 归约 0.142，均值 72.1 vs 90.7），active-set 规模从 2.233 增至 2.421。**自适应路由诊断**：学到的路由器在 Math 上平均 active-set 规模收敛到 **1.638**（非整数），达 **57.7 Avg@16 / 69.7 Pass@16**，证明可变 K_e 确被训练出来。

## 6. 亮点与贡献（Why it matters）

1. **流程无关的动作表示**：以"环境迁移边界"锚定优化单元，一套定义覆盖分工、联合共演、混合与学习式可变基数工作流，为 MAS-RL 提供了统一语言。
2. **接口极简、即插即用**：只改"策略动作"定义，rollout/奖励/优势/优化器全沿用，事件原子批处理是唯一新增工程要求。
3. **√K 归一化有理论支撑**：用方差分解把"独立保持尺度、相关显式贡献"讲清楚了，非拍脑袋的工程 trick。
4. **实证跨度较广**：数学 × 搜索，4 个模型规模（3B/4B/7B/8B），并给出梯度规模、响应长度、集合基数、事件完整性等训练动力学诊断。

## 7. 局限与可改进点（个人点评）

- **对比强度弱**：正文自认基线行是**跨论文引用而非配对重跑**，结论"描述性"、无显著性检验；数学场景对最强基线仅 +0.2 点，说服力主要靠搜索场景。
- **等算力比较缺失**：多智能体并行天然消耗更多推理算力，正文承认"固定计算预算下的优势尚待证明"；给出的 Utok 只是输出侧代理（不含 prompt、工具延迟、硬件占用），端到端成本收益存疑。
- **集合规模消融偏示意**：只做 K=5、单模型、单任务，未扫 K=2/3/4 与不同事件粒度。
- **成员 log-ratio 仍受长度影响**：作者自认序列级 log-ratio 依赖响应长度，长成员可能系统性抬高或稀释更新，未见长度正则或加权处理。
- **应用面窄**：仅数学 + 检索 QA，未见工具调用更密集、状态更异构的 agent 任务；并行智能体放大相关性检索错误的隐患也只作展望。
- **可复现性差**：多处"completed runs""additional machine"，未开源代码，三种子结果仅在特定机器运行。

## 8. 对我们的启示 / 可借鉴点

- **"更新单元对齐真实状态迁移"是可迁移的好原则**：GUI Agent 常是多角色系统（规划器 + 执行器 + 校验器），决定哪个单元接受梯度应由"这批输出是否共同改变了界面/DOM/应用状态"决定，而非角色书写顺序。
- **√K 归因归一化可直接借用**：并行采样多套 UI 动作路径合并成一个事件更新时，用基数归一化控制联合 log-ratio 量级，避免"动作越多、步长越大"的偏差。
- **事件原子批处理是好的工程实践**：同事件行必须同批、缺失即废弃，可直接落到轨迹采集管线，防止静默坏数据污染梯度。
- **分组相对优势适配异构事件**：GUI 轨迹长度差异极大（一次点击 vs 多步填表），把"可比事件"分组做组内标准化比绝对优势更稳。

**对 GUI Agent 的可借鉴点**：GUI Agent 本质是多角色系统——主策略决策、可能并行采样多个候选动作（点击 A 还是先滚动 B），由校验/汇总逻辑消费后触发一次真实界面提交。SRPO 的 active set 恰好为此提供训练范式：把并行采样的多候选动作与其消费方视为一个集合动作，分配基于任务成败的团队优势，用 √K 归一化防候选数放大更新，再整体裁剪一次。若在 GUI 的 Online RL（GRPO 系）中训练"规划—执行—验证"协同或"多候选并行探索"型 agent，可照搬其事件级批处理与组内相对优势，避免同一界面状态迁移被拆分到多步分别更新导致的 credit 噪声。此外，"动态路由决定每步 K_e"对 GUI 长任务很有吸引力：简单步走单例路径，复杂步（需先探测元素再决策）自动并行多个动作假设而训练目标不变，可自然衔接"动作分块/自适应"思路。最后，SRPO 强调集合动作必须在"同一 pre-action 状态"采样，也提醒我们做 GUI 并行动作采样时要**冻结一致的界面观测**，避免各候选看到不同屏幕快照。
