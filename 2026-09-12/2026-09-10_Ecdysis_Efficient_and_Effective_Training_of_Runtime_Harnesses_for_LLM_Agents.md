# ECDYSIS: Efficient and Effective Training of Runtime Harnesses for LLM Agents

> 一句话 TL;DR：把"harness 自演化"从"逐个失败改代码"改成"跨任务聚合失败模式 + 多角色诊断"，训练提速最高 1.84×、准确率相对提升 18.56%，且不训练任何模型权重。

## 2. 论文要解决的核心问题

- **要解决什么问题**：在**任务模型与运行环境完全冻结**下自动优化 Agent 的运行时 harness（规划、工具交互、上下文管理），并要在更少时间与 token 下比"逐个失败改代码"更好、更可泛化。属通用 Agent 方法论，任务为需持续改环境状态的工具调用。
- **为什么重要**：先导实验中 6 个 Qwen3 模型-领域组合上，去掉全部 harness 层平均 29.72%，固定人工 harness 达 50.28%，而"每次失败后串行改 harness"只有 43.33%，**反而低于不演化的人工配置**——harness 回报巨大，但自动演化是负收益。
- **现有方法的不足**：每次更新都要额外跑 agent + 改代码 + 验证，成本随失败数线性增长，演化还会逐步特化到已观测失败模式；根因是**缺少有原则的失败归因**——同一失败可能来自模型怪癖或 harness 系统性缺陷，单条失败不足以区分。
- **Research Gap**：论文问"跨任务实例的失败证据能否区分 model-specific accommodation 与 systematic harness repair"。它把失败从**修改信号降级为诊断证据**，以跨任务复现作为系统性缺陷的归纳偏置（作者声明是 inductive bias 而非因果证明）。

## 3. 方法核心思想（三层拆解）

### 3.1 一句话概括方法

每轮聚合失败轨迹、筛出覆盖 ≥2 个任务的复发失败组，让 Analyst / Critic / Engineer 在共享记录上精修 K 轮，由 Moderator 收敛成结构化修改规范，交 coding agent 改代码，仅在训练集总分严格提升时接受。

### 3.2 方法总览（Pipeline）

- **输入**：任务模型 θ、环境 E、训练集 D_train、初始 harness H_base、失败阈值 λ、演化轮数 R、精修轮数 K；**输出**：冻结的 H_F。
- **模块与连接**：①Collect（用 H_{i-1} 跑轨迹）→ ②失败判定 f_λ(τ)=I[S(τ)<λ]（评测框架固定）→ ③**轮级聚合**（记录任务 id、终止原因、工具调用历史；**优先保留覆盖 ≥2 任务的组**，单任务组仅作辅助；B_i 为空则跳过）→ ④**FDCR**（三角色顺序发言 × K 轮，Critic 负责反查触发过宽/误阻断/违约/回退风险）→ ⑤Moderator 产出规范（**不直接改代码**）→ ⑥coding agent 产出候选 → ⑦验收/回滚，把诊断规划与代码实现分离。

### 3.3 真正的创新点（去伪存真）

**真·方法创新**
- **把 harness 演化形式化为归因问题并给出可分解度量**：ΔH = t·ΔH_model + (1−t)·ΔH_harness，t 是迁就模型的决策占比，首次让"演化漂移"可人工标注、可量化（SE 60.0% vs ECDYSIS 45.5%）。
- **跨任务复发作为归纳偏置**：硬性要求失败组覆盖 ≥2 个任务，并明说这不是因果证明。
- **FDCR 的规范-实现解耦**：Moderator 作保守仲裁，Critic 承担风险与回退审查。

**工程组合**：多角色批评/迭代精修借自既有工作，轮级批处理、验收回滚、Life-Harness 基座与 OpenCode + DeepSeek-V4-Pro 均为集成。效率机理朴素：SE 每失败一次调用，ECDYSIS 每轮至多一次。

**对性能提升最关键的设计**：**轮级聚合是主要来源**——只加聚合（w/o FDCR）就把平均准确率从 46.67% 提到 54.67%、Pass^3 从 29.00 提到 42.00，时间降到 1,292.4s（零售，1.42×）/ 2,510.8s（航空，3.23×），成本降 70.71% / 66.53%。**FDCR 是"精度换成本"的二次增益**：59.33%、Pass@3 71.50、Pass^3 45.00，但时间回升到 1,405.9s / 4,403.0s。

**证据不足 / 仅声称有效**：无"只保留单任务失败组"的对照，故"≥2 任务"规则本身贡献多少未知；t 值来自人工分析，无样本量与一致性指标；FDCR 在强模型上有害（MiniMax-M2.7 在 τ²-Retail 上 100.00±0.00 → 96.67±2.89）且未解释；摘要的"1.84×"是 w/ FDCR 在航空子集的数字，同实验 w/o FDCR 达 3.23×。

## 4. 具体技术细节

### 4.1 模型结构

不训练任何模型权重。任务模型 Qwen3-8B / 14B / 32B、MiniMax-M2.7（230B）、Llama-3.1-8B 经 API 冻结调用，温度 0.0；演化只作用于 harness 代码（基座 Life-Harness），三种演化方法均从同一份人工优化 harness 出发；coding agent 与 FDCR 四个角色都用 DeepSeek-V4-Pro。

### 4.2 训练流程

**不训练模型参数**；被优化的是 harness 代码，过程如下：

| 阶段 | 目标 | 训练什么能力 | 数据来源 | 数据形态 | 目标 / 接受准则 |
|---|---|---|---|---|---|
| Collect | 拿本轮失败证据 | —（无参数更新） | D_train（两子集各 20 条训练任务，演化用 Qwen3-8B） | 执行轨迹（工具调用历史 + 终止原因） | 固定评测框架给分 S(τ)，f_λ=I[S<λ] |
| Aggregate | 从孤立失败升为复发模式 | 系统性缺陷识别 | 本轮所有失败轨迹 | 结构化记录 B_i，分组 G_i | 优先覆盖 ≥2 任务的组；B_i=∅ 则跳过 |
| FDCR | 把失败模式转成可实施规范 | 失败归因与修改规划 | G_i + 累积记录 M_i | 角色对话 + 规范 q_i | 三角色顺序发言 × K 轮（实验取 2），Moderator 收敛 |
| Edit | 产出候选 harness | 代码级修复 | q_i + 执行证据 + 源码 | harness 补丁 | coding agent 每轮**至多一次**调用（SE 则每失败一次） |
| Validate | 防退化 | — | 全训练集 | 训练集总分 J_train | 仅当 J_train(H^c) > J_train(H_{i-1}) 才接受，否则回滚；最多 3 轮候选 |

> 候选只在**后续完整评测**中评估，绝不在生成它的轨迹上评估。

### 4.3 推理流程

- **使用什么模型**：评测时把演化得到的 harness **冻结**，用 5 个任务模型分别跑；输入指令与环境状态，输出工具调用动作序列。
- **多步推理机制**：harness 负责规划、工具交互与上下文管理（ReAct 式循环 + 状态同步、实体解析、工具协调约束）；τ²-Bench 需要跨工具依赖、条件分支、状态前置与高风险操作确认。
- **评测协议**：每个测试任务独立跑 3 次并重置环境，每个"模型×子集×方法"共 60 条 held-out 轨迹；指标为 Accuracy、Pass@3（3 次至少 1 次成功）、Pass^3（3 次全成功）。测试期不做自适应。

## 5. Benchmark 与实验设置

### 5.1 Benchmark 一览表

| Benchmark | GUI 场景 | 任务类型 | 数据规模 | 输入格式 | 输出格式 | 评测指标 |
|---|---|---|---|---|---|---|
| τ²-Bench（Airline 子集） | General（工具调用/环境状态修改） | 多步、多意图、条件分支的客服类任务 | 训练 20 条 + 测试 20 条 | 自然语言指令 + 工具返回 | 工具调用动作序列 | Accuracy、Pass@3、Pass^3 |
| τ²-Bench（Retail 子集） | General（工具调用） | 同上，零售域 | 训练 20 条 + 测试 20 条 | 同上 | 同上 | 同上 |
| AgentBench | General | 相对简单的 agent 任务 | 完整评测矩阵的第三数据集 | 同上 | 同上 | 同上 |


### 5.2 实验结果分析

- **主结果（5 模型 × 2 子集平均）**：Direct 38.17%、Human-Aug. 51.67%、SE 46.67%、ECDYSIS(w/o FDCR) 54.67%、**ECDYSIS(w/ FDCR) 59.33%**；Pass@3 为 53.50 / 66.00 / 63.50 / 66.50 / **71.50**，Pass^3 为 22.50 / 37.00 / 29.00 / 42.00 / **45.00**。相对 SE 提升 27.1%、相对 Human-Aug. 提升 14.8%，Pass^3 相对 SE 提升 55.2%。推理 token 11.57M → 10.16M（−12.19%）。
- **跨模型泛化（只用 Qwen3-8B 演化 harness）**：Qwen3-8B 在 τ²-Airline 从 35.00% → 60.00%（Pass@3 50.00 → 80.00）；未参与演化的 Qwen3-32B 同子集从 51.67% → 68.33%。完整矩阵平均 58.67%（SE）→ 69.56%（w/ FDCR），相对提升 18.56%。
- **效率与成本**：端到端训练时间 τ²-Retail 1,831.4s → 1,292.4s（1.42×）/ 1,405.9s（1.30×）；τ²-Airline 8,120.6s → 2,510.8s（3.23×）/ 4,403.0s（1.84×）。API 总成本 SE $8.484 / $6.382 → w/o FDCR $2.485 / $2.136（降 70.71% / 66.53%）→ w/ FDCR $5.763 / $2.609（降 32.07% / 59.12%）。另：SE 在 τ²-Retail 上约 67% 的 coding-agent 调用正常完成，ECDYSIS 在两域上**全部正常完成**。
- **Ablation 结论**：①**SE → w/o FDCR**（只加轮级聚合）Accuracy +8.00pp、Pass@3 +3.00、Pass^3 +13.00——聚合同时提升性能与效率，说明"逐个失败串行改"不仅贵，还会因重复修改而变差；②**w/o FDCR → w/ FDCR** 再 +4.67pp / +5.00 / +3.00，是独立精度增益，但航空上时间从 2,510.8s 涨到 4,403.0s；③**t 值**：SE 60.0% vs ECDYSIS 45.5%，把"泛化更好"与"少迁就模型"联系起来。

## 6. 亮点与贡献（Why it matters）

1. **提出并量化了一个此前含糊的问题**：harness 演化在修 harness 还是在迁就模型？ΔH 分解与 t 值让这个问题可测量，也给自演化漂移提供了可监控指标。
3. **效率账算得干净**：收益（1.42×–3.23×、成本降 66%–71%）来自可证明的调用次数不等式 N_round ≤ N_serial。
4. **泛化证据是跨模型的**：harness 只用 Qwen3-8B 演化，却在 Qwen3-32B 与 MiniMax-M2.7 上继续涨，是"改的是系统性机制而非模型怪癖"的有力验证。

## 7. 局限与可改进点（个人点评）

- **统计功效偏弱**：每子集只有 20 条测试任务、3 次试验，Direct 标准差高达 ±28.575；论文把 230B 的 MiniMax（基线 90%）与 Llama-3.1-8B（8.33%）混在同一平均里，平均值由模型构成主导，相对提升被低基线模型放大。应报告分层提升与配对检验。
- **t 值证据链不透明**：60.0% 与 45.5% 是人工标注结果，却没有样本量、标注者数量与一致性指标；作为解释泛化优势的关键量，这个缺口比实验数字更值得补。
- **FDCR 的收益并非单调**：在 MiniMax-M2.7 与 Qwen3-14B 的部分单元格上加 FDCR 反而更差，合理解读是"保守的 Critic 在强模型上误伤有效改动"，但论文未做机制分析。

## 8. 对我们的启示 / 可借鉴点

- **给"自动改自己"的 pipeline 加一道归因闸门**：把失败写进待修清单前先问"它是否在 ≥2 个不同实例上以同一机制复现"，否则只归档不修改。这条规则近乎零成本，却能挡住大部分过拟合式补丁。
- **把"修改信号"与"修改实现"解耦**：诊断/规划由多角色 LLM 阶段产出结构化规范，落地交给另一个 coding agent 阶段——规范可审计、可回滚。
- **验收用"严格提升 + 回滚"**：候选只在后续独立评测上验证，降低自演化中的自我确认偏差。

### 对 GUI Agent 的可借鉴点

1. **GUI 失败归因尤其需要跨实例聚合**：单条 GUI 失败极难归因——可能是截图分辨率/坐标缩放导致点偏（harness 缺陷），也可能是模型视觉定位不足（模型缺陷）。可把失败按"动作类型 + 失败阶段（观测/定位/输入/提交）"分组，**只修在 ≥2 个不同 App 上重复出现的组**。
2. **把"观测-动作契约"当作一等公民来演化**：本文 Critic 专门检查"触发过宽、误阻断合法行为、违反运行时契约"。映射到 GUI：新增规则不能变成"全局禁止点击某类元素"，否则会像论文观察到的那样**缩小合法动作空间**、降低跨 App 泛化；每条约束应标注作用域（App / 控件 / 全局）与回退条件。
3. **数据侧优先选"新执行路径"而非"更多条数"**：本文 1/4 数据即达全量效果，而 GUI 采样成本高，应优先挑能触发新交互结构（新控件类型、新弹窗流程）的任务作为演化探针。
