# terms.txt: A Consent and Compensation Protocol for Agentic Web Access

> 一句话 TL;DR：为 Agent 抓取网页提出 robots.txt 式的 terms.txt 条款文件 + 源站自执行的签名/委派/402 协商/收据交换，把同意与补偿落回 HTTP 边界，每请求仅增 0.20–0.65 ms。

## 2. 论文要解决的核心问题

- **要解决什么问题**：开放网络"站点允许抓取、搜索引擎回流访问者"的不成文交易正在 AI 爬虫与 Agent 面前崩塌。论文要解决**站点如何对机器访问表达可执行条款**——按路径、按用途、可计价的同意与补偿，场景是 Web 平台层的 HTTP 请求边界。
- **为什么重要**：公开测量显示抓取与回流已脱钩：自动化客户端占多数（Cloudflare 2026-06 为 57.5%）；crawl-to-refer 比传统搜索约 5:1，而 Anthropic 爬虫 2025-06 约 **70,900:1**（1 月 286,000、7 月 38,000，降 87% 后仍最重）；训练占 AI 专用爬虫请求从 72% 升到 79%。抓取照旧、点击消失（Pew：AI 摘要出现时点击传统结果从 15% 降到 **8%**，点摘要引用仅 **1%**，直接结束会话从 16% 升到 **26%**），补偿必须被协议化。
- **现有方法有什么不足**：robots.txt（RFC 9309）四重失败——**政策不自洽**（Longpre 审计 14,000 域名：AI 爬虫限制从近乎不存在涨到覆盖语料 >5% token，服务条款覆盖 45% 的 C4 且常互相矛盾）、**无法达成一致**（GPTBot 同时是最明确禁止与允许的爬虫）、**不被可靠遵守**（2025-08 Cloudflare 记录 Perplexity 用未声明 user agent 抓已禁站点）、**该精确处太粗糙**（超 1/3 请求来自混合用途 bot）。替代方案各有缺口：Web Bot Auth 无授权/委派/意图词表，AIPREF 排除强制与认证，Pay Per Crawl/Fairfetch 只能经代理计价。
- **Research Gap**：缺口是**身份 + 用途 + 条款/价格 + 委派在同一 HTTP 边界上同时可表达且源站可自执行**。作者贡献：汇编测量、论证 robots.txt 失效、给出 terms.txt 规范并测成本。

## 3. 方法核心思想（三层拆解）

### 3.1 一句话概括方法

在 HTTP 请求边界把已有标准件（Web Bot Auth 签名、RFC 9421 消息签名、HTTP 402、x402 结算）组合成一次请求—响应流：源站发布 `/.well-known/terms.txt` 表达按路径按用途的条款，客户端在签名中携带意图/委派/支付凭证，源站本地验证并返回签名收据。

### 3.2 方法总览（Pipeline）

- **输入 / 输出**：输入为普通 HTTP 请求（最多六个头部）+ 运营者签名密钥、可选委派令牌与支付凭证；输出为内容 + 签名 `Access-Receipt`（写入哈希链日志），或 `402`（附价格与条款）、`401`、`403`。
- **terms.txt**：发布在 `/.well-known/terms.txt`；头部声明条款版本、收据签名密钥目录与结算方式，每个 `Path:` 块为未签名请求设规则，并对每个用途给出 allow / charge / deny。用途词表为 **search / agent / train-ai / archive / research**，use 等级沿用 Content Signals 的 **immediate / reference / full**；文件本身不强制，强制来自配对交换。
- **六个头部与验证顺序**：`Signature-Agent`、`Signature-Input`、`Signature`（RFC 9421 覆盖方法与路径、agent 成员与三个 Access 头部；5 分钟有效、含 nonce 与 JWK 指纹）、`Access-Intent`（RFC 9651 字典，如 `purpose="agent", use="reference"`）、`Access-Delegation`、`Access-Payment`。源站按序：验签 → **发现式抓取前原子预留 nonce** → 解析意图 → 检查委派与范围 → 评估条款 → 验证支付 → 服务并签发收据；未签名请求走公开路径，受保护路径返回 403。
- **四类客户端与委派**：训练爬虫、搜索爬虫、服务运营 Agent、**用户委派 Agent**（为具体个人抓取，继承权益但不暴露身份）。委派令牌把**成对假名主体**绑定到运营者、具名范围与过期时间；每请求返回签名 `Access-Receipt` 并追加到**哈希链式日志**，违约则**撤销资格**。

### 3.3 设计主张的层次拆解（去伪存真）

**① 真·设计贡献**：**terms.txt 的语义位置**——不是又一份声明式偏好文件，而是**与强制机制配对**的条款文件；**把"用户委派 Agent"立为独立客户端类**且继承权益而不暴露身份；**收据作为与计价单位解耦的会计原语**；**诚实的边界声明**——区分交付前可强制、交付后可审计、只能留给合同。

**② 工程组合**：RFC 9421、Web Bot Auth（2026-09-01 成为 IETF Standards Track）、Signature Agent Card、RFC 9651、HTTP 402、x402、Content Signals 全部复用。

**③ 对可行性最关键的设计**：①**"拒绝比服务便宜"**——Ed25519 验证中位 120 µs，伪造签名 0.21 ms 被拒、402 路径 0.37 ms 低于付费 0.65 ms；②**nonce 在发现式抓取前原子预留**，修掉第一版"两个相同签名请求竞争冷密钥查找"的 bug；③**无代理的源站中间件**（核心交换约 550 行）。

**④ 证据不足 / 仅声称有效**：性能只在 loopback（无 TLS、单核共享压测器）成立，0.20–0.65 ms 是**下界**；吞吐从约 15,900 降到 1,400–3,000 req/s，缓解方案未实现未测量；**无真实站点部署**；**虚假用途声明事前无法阻止**；**无法阻止未签名抓取**；**撤销依赖中间方**。

### 4.3 推理流程

不适用（无模型推理）。对应**每次请求的处理流程**：验签 → 原子预留 nonce → 解析意图 → 检查委派与范围 → 评估条款 → 验证支付 → 服务并签发收据 / 返回 402 / 401 / 403。密钥目录按 `(URL, key)` 缓存，每 agent origin 每进程抓取一次（loopback 约 35 ms）。

## 6. 亮点与贡献（Why it matters）

1. **把"同意"从偏好变成可强制条款**：llms.txt / ai.txt / Content Signals 都是"只有声明没有牙"，本文给出配对强制机制，并区分"可强制 / 可审计 / 只能靠合同"。
2. **"用户委派 Agent 继承权益但不暴露身份"填补真实语义缺口**，现有商业方案没有对应抽象。
3. **对标准草案的实质纠错**：指出 Web Bot Auth 草案打印的签名基遗漏 `Signature-Agent` 引号、测试向量只有加引号才通过。
4. **"让计价单位可测量"而非规定计价单位**：Cloudflare 一年内从 per-crawl 转向 per-use，与计价解耦的收据是高明取舍。

## 7. 局限与可改进点（个人点评）

- **性能结论外部效度最弱**：loopback、无 TLS、单核共享压测器，而"拒绝比服务便宜"恰恰依赖这些理想条件；真实部署中 TLS 与 RTT 会淹没 0.20–0.65 ms 增量，但**单线程 Ed25519 把吞吐砍到约 1/5 至 1/10** 不会，对小站点可能是真问题。
- **协议只保护"愿意谈判的双方"，且部署动机不对称**：不签名就能抓取、虚假用途声明事前无法阻止，因此它在**最需要保护的小出版商**身上效果最弱——既要自己观察行为才能发现违约，又要依赖中间方执行撤销；站点还需部署中间件、维护密钥目录与收据日志，而爬虫方不部署没有惩罚，**先动成本全在站点**（EU AI Act 第 53(1)(c) 条只覆盖训练用途）。
- **条款语义的可判定性未被讨论**：多个 Path 前缀重叠、use 等级与实际行为不匹配时如何裁决，没有形式化语义与优先级规则——这恰是 robots.txt 四十年来最易出 bug 之处。

## 8. 对我们的启示

- **Web GUI Agent 的抓取合规不能只靠 robots.txt 声明**。我们的 Agent 若在 Web 平台采集页面（grounding、检索、数据构造），当前通常读 robots.txt 就动手。terms.txt 的启示是**应把"条款"与"身份"一起实现**——Agent 侧需具备签名身份（Web Bot Auth）、可声明用途（`Access-Intent`）与承载用户委派令牌的能力，否则未来在合规站点上只能拿到公开路径。
- **站点协商会直接改变 GUI Agent 的可行动作空间**。源站按用途 allow/charge/deny 后，同一页面在不同用途下可访问性不同，甚至返回 402 而非内容。规划层必须处理 **402/401/403 的语义分支**（申请凭证、降级到公开路径、报告受限），而非把非 200 当"页面不存在"或无限重试。
- **收据 + 哈希链日志是可复用的审计范式**：`Access-Receipt`（运营者、假名主体、用途、条款 ID、路径、签名哈希、时间戳）可直接借鉴为轨迹级 provenance 记录；"用户委派"的成对假名 + 运营者绑定 + 具名范围 + 短期有效期，也是 Agent 代表用户访问第三方服务的正确方向。
