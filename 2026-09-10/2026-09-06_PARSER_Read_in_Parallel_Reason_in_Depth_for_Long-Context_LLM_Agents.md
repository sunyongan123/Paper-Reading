# PARSER: Read in Parallel, Reason in Depth for Long-Context LLM Agents

> 一句话 TL;DR：把长文档的顺序压缩式阅读，改为"并行块阅读 + 按需多轮深挖"的 lead–subagent 架构，让推理深度随问题复杂度而非文档长度增长。

## 2. 论文要解决的核心问题

**要解决什么问题**：长文档推理。给定一篇长达数十万 token 的文档和一个需要跨段证据的多跳问题，让 LLM Agent 给出准确答案。

**为什么重要**：长上下文是 LLM 的核心能力，但即便窗口已到百万 token 级，准确率仍随输入变长而下降——即 **context rot（上下文腐化）**，典型表现是位置偏置：中段证据被系统性忽略。作者在多跳 QA 上复现：文档从 7K 涨到 896K token 时，直接全上下文作答会掉几十分。既然窗口远未用满就退化，瓶颈就**不是容量，而是"该读什么、按什么顺序推理"**。

**现有方法有什么不足**：主流应对是**顺序记忆范式**（MemAgent 及后续 ReMemR1、GRU-Mem）——逐块读文档，每步把当前块与旧记忆压成新记忆，最后只凭记忆作答。它解决了"有界工作记忆 + 任意长度 + 端到端可训练"，但有一个结构性承诺：**文档恰好按顺序被遍历一次**，由此带来两个后果：
1. **对证据分布敏感**——每块被压缩时还看不到后文，判断相关性处于信息赤字，准确率受证据位置、逻辑顺序与间距影响；这在多跳推理中最致命，因为后一跳的相关性往往要等前一跳找到后才显现。
2. **延迟线性增长**——第 t 块更新依赖第 t−1 块，T 个块构成不可约串行链。

**Research Gap**：作者的核心论断是——**文档的阅读顺序由文档规定，问题的推理顺序由问题规定；顺序记忆 Agent 让前者错误地驱动了后者**。他们补的缺口正是把这两者解耦：阅读可以并行且对称，串行只留给问题所需的推理深度。

## 3. 方法核心思想（三层拆解）

### 3.1 一句话概括方法

ParSer（**Par**allel Reading + **S**equential **R**easoning）用一群轻量子 Agent 并行扫完全文，由一个只持问题、从不看原文的主 Agent 用多轮 scatter–gather 逐步深挖，只训练主 Agent。

### 3.2 方法总览（Pipeline）

- **输入**：长文档 D + 问题 q。
- **输出**：答案 a（与金标精确匹配）。
- **模块与连接**（lead–subagent 的 scatter–gather）：
  1. **并行块阅读器（subagents）**：文档切成定长块，每块绑定一个轻量子 Agent；给定主 Agent 的查询，子 Agent 只依据自己那块返回"发现（finding）"或弃权（abstain）。所有子 Agent 每轮并发执行。
  2. **问题驱动的推理者（lead agent）**：主 Agent 输入只有问题 q，永远看不到文档或任何原始块。它以 ReAct 风格多步循环：思考后要么发起一次 scatter–gather、要么给出最终答案，每轮查询以"已收集到的发现"为条件。
  3. **跨轮自适应并行阅读**：跨块依赖由推理轮次承载——第 k 轮发现进入主 Agent 上下文，条件化第 k+1 轮查询，从而把"按文档顺序传播记忆"转为"按问题驱动的查询链"。
- 数据流：`q → lead 思考 → scatter 并发查询 → 各块 finding/abstain → gather → lead 再思考 →（循环 K 轮）→ 答案`。K 由问题所需推理跳数决定，而非块数 T。

### 3.3 真正的创新点（去伪存真）

- **真·方法创新**：① 把"T 步串行记忆更新"重构为"K 轮并行 scatter–gather"，让关键路径随**推理复杂度**而非文档长度增长；② **对称访问机制**——每轮所有块在同一查询下被重新审视、且不被永久丢弃，从机制上根除"中段证据被后续记忆覆盖"这一 context rot 根源。这是顺序记忆范式做不到的。
- **工程组合**：lead–subagent、scatter–gather、ReAct 循环、GRPO + RLVR 都是既有组件，本身不新。
- **对性能提升最关键的设计**：消融显示**"分块并行 + 对称访问"是核心**——去掉分块平均分从 84.6% 掉到 73.76%（佐证 context rot）；子 Agent 规模从 2B 换 4B 提升明显（78.26%→84.57%），再换 9B 饱和。次关键的是"只训主 Agent"带来的极简训练成本。
- **证据不足 / 仅声称有效**：作者强调"高效"（11× 加速），但这是**延迟视角**；并行意味着每轮重读所有块的 prefill，若无 KV-cache 复用，计算量可能不降反升。且实验用异构硬件（1×H100 子 Agent + 1×RTX3090 主 Agent）对单 GPU 基线，"交替执行故可比"的说法说服力有限。

## 4. 具体技术细节

### 4.1 模型结构

- **base model**：Qwen3.5-4B / 9B，是 **LLM（纯文本，非 MLLM，无视觉编码器）**。
- **角色分工**：子 Agent（block reader）冻结；主 Agent（lead/reasoner）是唯一被训练的对象。

### 4.2 训练流程

| 阶段 | 目标 | 训练什么能力 | 数据来源 | 数据形态 | 训练目标 / Loss |
|---|---|---|---|---|---|
| 单阶段 RLVR | 学会"按需发查询、逐步深挖"的策略 | 主 Agent 的查询生成与终止决策 | HotpotQA 合成 | 32,768 条，每条约 200 段、约 28K token | 奖励=二值精确匹配 EM(a_pred, a_gold)，优化器 GRPO，策略梯度中**掩掉 observation token**（只对主 Agent 生成 token 回传梯度），全异步 RL |

> 关键设定：不用格式奖励；训练上限 9 轮、块 512 token；推理放宽到 12 轮、块 4,096 token。

### 4.3 推理流程

- 使用**训练后的主 Agent + 冻结子 Agent**。
- 推理输入 = 问题 q（主 Agent）＋ 各块（子 Agent）；输出 = 答案 a。
- **多步推理**：主 Agent 以 ReAct 风格循环，交替"思考→发查询（scatter）/终止作答"，终止条件是主 Agent 决定给出最终答案；实际轮数 K 由问题推理跳数决定。

## 5. Benchmark 与实验设置

### 5.1 Benchmark 一览表

| Benchmark | GUI 场景 | 任务类型 | 数据规模 | 输入格式 | 输出格式 | 评测指标 |
|---|---|---|---|---|---|---|
| HotpotQA | General（非 GUI） | 多跳问答 | 合成 32,768 训练 / 评测集 | 长文档(7K–896K token) + 问题 | 答案 | Sub_EM |
| 2WikiMultiHopQA | General（非 GUI） | 多跳问答（域外泛化） | 标准评测集 | 长文档 + 问题 | 答案 | Sub_EM |

> 说明：本文并非 GUI 落地论文，benchmark 均为长文档多跳问答；对 GUI Agent 的价值在"可迁移方法"层面（见第 8 节）。

### 5.2 实验结果分析

- **主结果**：ParSer 用 4B/9B 底座平均 **84.6% / 86.8%**，比最强顺序记忆基线高 **5.7 / 6.7 个百分点**；在最长 896K 设置上差距扩大到 **12.0 / 9.9 个百分点**。9B 版平均 86.8%，**超过原生支持百万 token 的 DeepSeek-V4-Pro 6.3 个百分点**；域外 2Wiki 上 9B 平均 88.48%，顺序基线明显下滑而 ParSer 稳定。
- **三项受控实验**：① 证据位置——894K 文档中把证据放到 0–90 分位，ParSer 曲线平坦，MemAgent 在 50–70 分位塌陷（中段证据最易被覆盖）；② 证据顺序——反转两跳逻辑顺序，MemAgent 从 66.5% 掉到 23.3%，ParSer 保持 96.4%→97.1%；③ 证据距离——随干扰段增多 MemAgent 50.0%→44.6%，ParSer 稳定 87%–88.7%。
- **Ablation 说明什么**：① **子 Agent 规模**：2B→4B 提升明显（78.26%→84.57%），4B→9B 饱和（84.77%），说明块阅读能力存在阈值、不必无限加大；② **去掉分块**：平均降到 73.76%，直接证明 context rot 是主要瓶颈、分块并行是解药；③ **主 Agent 可插拔性**：不重训即可兼容思考型（85.55%）与 DCI（84.67%）子 Agent，说明架构解耦有效；④ **推理延迟**：单并发 896K 时 11× 加速（78.2s vs 876.2s），并发 16 时仍 1.7×。

## 6. 亮点与贡献（Why it matters）

- **依赖结构重写**：把"T 步串行更新"换成"K 轮并行 scatter–gather"，关键路径随推理复杂度而非文档长度增长，对称访问根除"中段证据被覆盖"。
- **训练极简化**：只训主 Agent、子 Agent 冻结，训练成本与文档长度解耦；主 Agent 从不直接看文档，学到的是通用"问题推理"而非"文档摘要"，域外泛化更好。
- **工程可插拔**：主 Agent 与不同子 Agent 实现解耦，可自由替换 OCR/DOM/视觉定位等局部理解器。

## 7. 局限与可改进点（个人点评）

- **任务面偏窄**：评测集中在 HotpotQA 与 2WikiMultiHopQA，训练数据只由 HotpotQA 合成；法律、代码库、多文档综述等更开放任务未验证。
- **"高效"结论不完整**：并行重读带来 prefill 重复，若无 KV-cache 复用计算量可能不降反升；异构硬件对比的说服力不足。
- **弃权机制的静默风险**：若冻结子 Agent 漏检（把有证据的块判为无关），主 Agent 无法察觉，错误被静默放大；且方法假设问题能分解为"单块内可独立判定"的查询，对必须跨块联合判定的任务可能不成立。

## 8. 对我们的启示 / 可借鉴点

**对 GUI Agent 的可借鉴点**（本文为 Agent 方法论域，非 GUI 落地）：
1. **"读"与"想"解耦**：把超长截图序列 / 超长 DOM / 历史轨迹切成块，交给轻量子 Agent 并行"读"，主 Agent 只持任务目标与各轮汇总的"发现"，不把全部像素塞进上下文——正对 GUI 的"上下文爆炸"与"中段信息被忽略"两大痛点。
2. **按需深挖替代一次性全屏理解**：先问"哪个区域含目标控件"，据返回再追问"该控件精确坐标/状态"，用多轮 scatter–gather 承载跨屏依赖。
3. **历史步骤的物理顺序不应决定推理顺序**：否则长流程任务会像顺序记忆一样退化。
4. **只训规划/查询的主 Agent、冻结"看局部画面"的视觉子 Agent**：低成本范式，子 Agent 可插拔（OCR、DOM 解析、视觉定位模型）。差异点：GUI 观察像素级、冗余高、实时性强，块划分应按 UI 结构而非固定长度，轮数须严格预算。
