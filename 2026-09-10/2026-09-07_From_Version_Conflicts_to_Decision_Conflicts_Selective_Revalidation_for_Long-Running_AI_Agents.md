# From Version Conflicts to Decision Conflicts: Selective Revalidation for Long-Running AI Agents

> 一句话 TL;DR：区分"版本冲突"与"决策冲突"，用可执行前提 + 反向索引做选择性再验证，让长运行 Agent 在状态变化后只重验受影响前提，既保住无害决策又拦住失效动作。

## 2. 论文要解决的核心问题

- **要解决什么问题**：长运行 Agent 存在"读状态"与"对外执行动作"之间的结构性时间裂缝——Agent 观察到状态后，可能经历推理、工具等待、人工审批、暂停/恢复，很久之后才真正执行副作用（如发起退款）。期间支撑该动作的状态完全可能已变。论文要回答的核心问题不是"状态变没变"，而是"这个变化是否让待执行动作的正当性失效"。

- **为什么重要**：这是所有带外部副作用的自主 Agent（退款、云修复、采购等）的通用痛点。若变化被忽略（NoCheck），会放行已经失效的危险动作（重复退款、超额支出）；若一有版本变化就全盘作废重规划（VersionAbort），则把大量无害决策也丢弃，浪费推理与人工审批成本。作者用贯穿全文的退款例子量化了这种两难：额度 100→90 仍满足 80≤90（应放行），额度降到 50 或同事已退款则必须拦下——同样的"版本号 +1"，语义后果截然不同。

- **现有方法有什么不足**：论文明确批评两类范式。一是**乐观并发控制 / 版本检查（OCC）**：它只能报告"你读的是版本 11、现在已是 12"，无法判断变化的字段是否影响决策正当性，属于"数据执行层"判据；二是**语义可串行化**：虽能用应用语义放宽正确调度集合，但仍是事务执行的正确性准则，而 Agent 跨数据库/API/文档推理、长时间暂停，挂起一个事务既不现实也不充分。二者都未回答"变化是否推翻决策理由"这一更细粒度问题。

- **Research Gap**：作者 self-claim 的缺口是——在"观察"与"副作用"之间缺少一层**决策校验层**：版本变化应是"触发检查的信号"而非"自动作废决策的理由"。论文贡献三点：(1) 一个区分版本冲突与决策冲突的模型；(2) 带四种运行结果（KEEP/REFRESH/REPLAN/BLOCK）的反向索引协议 + 目标侧校验态绑定；(3) 可执行原型与对安全性、选择性、扩展性、竞态、依赖遗漏的受控评测。作者明确自限：这证明的是"受控可行性"而非生产通用性或前提自动抽取。

## 3. 方法核心思想（三层拆解）

### 3.1 一句话概括方法

把支撑决策的"可执行前提"显式记录下来，用反向索引在状态变化时只重验受影响的下游前提，再用目标侧事务/CAS 绑定校验结果，形成"观察—决策—执行"之间的窄校验层（ATR）。

### 3.2 方法总览（Pipeline）

- **输入**：一个已记录的 Agent 事务 `T = ⟨R, D, I, E⟩`（读集合 R、决策 D、待执行意图 I、外部副作用 E）构成的有向依赖图；一个变化事件 x（版本变化触发或 PRE_EFFECT 执行前触发）。
- **输出**：四档校验结果之一（KEEP / REFRESH / REPLAN / BLOCK）+ 是否放行副作用的 apply 状态。

- **模块与连接**（图 1 数据流）：
  1. **依赖捕获**：把读到的证据（如 delivered=true、amount=80、refund-limit=100）与决策、意图、副作用连成不可变图 `R→D→I→E`，每条边表"可能依赖"。
  2. **变化定位**：`normalize_event` 把变化转成"资源/字段对"Δ；PRE_EFFECT 时再 `version_diff` 比对所有必需证据 token。
  3. **受影响闭包**：用哈希反向索引从匹配的读出发，定位能到达待执行动作的下游子图 `C_aff`。
  4. **前提重验**：对 `C_aff` 的每个必需类型化前提调用确定性校验器 `f`，取最高严重度（BLOCK > REPLAN > REFRESH > KEEP）。
  5. **目标侧绑定**：按 `binding_policy` 决定绑定集 B(e)，若允许则 `conditional_apply(e, b)` 经原生事务/CAS 原子提交；被拒则重新校验。

### 3.3 真正的创新点（去伪存真）

- **真·方法创新**：① **版本冲突 ≠ 决策冲突**的概念切分，以及四档严重度（KEEP/REFRESH/REPLAN/BLOCK）的运行时响应语义；② **类型化前提（typed premise）**作为再验证对象——明确拒绝把自由文本思维链当前提，要求前提映射到可重复执行的确定性校验器，模型生成的前提在被映射前视为不可信；③ **反向索引 + 受影响闭包**的选择性重验协议，配合目标侧 checked-state binding 关闭 time-of-check/time-of-use 竞态。
- **工程组合**：不可变记录、SHA-256 摘要、哈希反向索引、append-only JSON 说明、内存目标 token 检查、SQLite 测试床——都是成熟组件，本身不新，组合成一个紧凑运行时（Python 3.11）。
- **对性能提升最关键的设计**：反向索引带来的**选择性**是核心收益——每次变更平均只评估 0.6 个前提（FullScan 为 6.0），且无关记录从 13 增到 4,093 时延迟几乎不变（8.8→9.3 μs，FullScan 12.1→2595.9 μs）。
- **证据不足 / 仅声称有效**：论文**从未声称**能自动可靠抽取前提——这一步被明确跳过，是最大未验证环节；命题 1 的安全性高度依赖"依赖完备、校验器可靠、token 忠实、观察绑定、目标原子执行"五条假设，任何一条不成立（尤其依赖遗漏）安全性即线性恶化。

## 4. 具体技术细节

### 4.1 模型结构

**无 base model**。本文是纯工程运行时原型，不含任何 LLM/MLLM、视觉编码器或训练。核心是一个 Python 3.11 紧凑运行时：不可变 read/decision/intent 记录、SHA-256 值摘要、哈希反向索引、类型化 Python 校验器、append-only JSON 记录、暴露版本 token 单元检查的内存目标；SQLite harness 测试两客户端竞态、持久化 checkpoint/resume 与跨资源提交。序列化图每次 trace 平均 7.4 KiB（含 48 个额外上下文读，为未压缩原型表示，非存储下界）。

### 4.2 训练流程

无训练阶段（无 SFT / RL / 蒸馏）。ground truth 与校验器均为 developer-authored 的确定性业务规则，oracle 即"定义每个 mutation 类别所用的同一显式业务规则"，**无 LLM 标注结果**。

### 4.3 推理流程

- 运行时采用**事件驱动校验**（非 LLM 多步推理）。两条触发路径：变化事件（change stream/webhook 仅作 early-warning 优化，非正确性路径）与 PRE_EFFECT 执行前校验。
- 核心算法 `Validate(x, e)`：`normalize_event` 求 Δ → 若 PRE_EFFECT 则补读必需证据并 `version_diff` → 反向索引求 `C_aff` → 对每个必需前提按缺失/可验证情况补读并调用 `validate(p, obs)` → 取最高严重度 → `binding_policy` 求绑定集 → 若允许则 `conditional_apply(e, b)`，被拒则 `schedule_revalidation` → `append_explanation` 追加只增说明。
- **关闭校验-执行竞态**：对目标侧前提，把校验过的目标版本传入原生事务/CAS/唯一约束/租约/领域命令，条件失败则重验或阻断；对外部策略/预算/授权资源（其变化未必推进目标版本），需强绑定（目标事务检查这些版本或等效 reservation/lease/fencing token），否则记为"未绑定"并把残余竞态暴露给策略层，不可逆副作用应 fail-closed。
- 复杂度：命题 2 给出受影响闭包 `O(|A_c| + |V_c| + L)`（L 为查找成本）。

## 5. Benchmark 与实验设置

### 5.1 Benchmark 一览表

> 本文非 GUI benchmark，而是三个 deterministic 可执行工作负载（workload），用确定性规则代替模型输出。

| Benchmark/Workload | 场景 | 任务类型 | 数据规模 | 输入格式 | 输出格式 | 评测指标 |
|---|---|---|---|---|---|---|
| refund（退款） | General（非 GUI） | 决策再验证 / 事务闸门 | 5 变更 × 10,000 轨迹 × 7 seed | 证据字段（delivered/defect/refunded/amount/limit）+ 版本 token | KEEP/REFRESH/REPLAN/BLOCK | 误放行率、误阻断率、前提数、延迟 |
| cloud remediation（云修复） | General | 决策再验证 | 同上 | incident state / restart authority / maintenance freeze | 四档结果 | 同上 |
| procurement（采购） | General | 决策再验证 | 同上 | request state / vendor / budget / auto-approval / authority | 四档结果 | 同上 |

每 workload 5 种变更 = 1 KEEP + 1 REFRESH + 1 REPLAN + 2 BLOCK，故固定变更组合中 40% 对现有意图安全、60% 不安全。总计 7 组打乱种子调度、每 workload 每次 10,000 轨迹，共 **210,000 次受控执行**（对应 15 个语义变更用例，非 210,000 个不同场景）。另建 10 个 SQLite 持久化工作流单元（10 cells × 10 次 × 4 方法 = 400 次方法执行）。

### 5.2 实验结果分析

**主结果（表 3）：**

| 方法 | 不安全放行率 | 安全却重规划率 | 每次变更前提数 | p50 延迟 |
|---|---|---|---|---|
| NoCheck | 100.0% | 0.0% | — | — |
| VersionAbort | 0.0% | 100.0% | — | — |
| FullScan | 0.0% | 0.0% | 6.0 | 39.9 μs |
| **ATR** | **0.0%** | **0.0%** | **0.6** | **10.8 μs** |

- NoCheck 放行 126,000 次无效副作用（60.0%）；VersionAbort 未放行但把全部 84,000 次安全变更重规划；ATR 与 oracle 完全一致（0 误放行、0 误阻断）。
- **持久化单元**：NoCheck / VersionAbort 精确结果匹配率仅 40% / 20%，FullScan 与 ATR 各 100%。
- **成本与扩展性**：ATR p50/p95/p99 = 10.8 / 13.0 / 20.5 μs；谓词粒度遍历平均 2.6 节点（p95 3）vs 整对象捕获 6.4（p95 8）；无关读 13→4,093 时 ATR 8.8→9.3 μs，FullScan 12.1→2595.9 μs（约 280 倍）。

**Ablation / 机制验证说明了什么**：
- **竞态**：7,000 对两客户端 SQLite 并发更新，每对恰好一个提交（0 双提交 / 0 零提交）——验证绑定模式，非分布式行为。
- **跨资源绑定（关键消融）**：仅目标侧 CAS 会在策略上限已为假后仍提交 100/100 次；加入被检查的策略 token 后拒绝 100/100 次——证明"目标侧绑定"是跨资源安全性的必要条件。
- **不可用校验器**：3 个定向测试全部返回 BLOCK（fail-closed）。
- **依赖遗漏故障注入（最关键警示）**：随机删除唯一关键依赖边，1% / 5% / 10% 遗漏率对应误放行 0.95% / 5.05% / 9.97%（近似线性）——**选择性校验只有在依赖捕获完备或保守过近似时才安全**。

## 6. 亮点与贡献（Why it matters）

1. **概念切分干净、可迁移**："版本冲突 ≠ 决策冲突"给出第三条路，摆脱"无视变化（危险）"与"全盘作废（浪费）"的非此即彼。
2. **把"可执行前提"而非"自由文本理由"当作再验证对象**：模型生成的推理在映射到确定性校验器前视为不可信，从架构上隔离了 LLM 非单调推理与确定性把关。
3. **同时拿到安全性与选择性**：受控实验中误放行/误阻断均为 0，每次变更仅 0.6 前提，延迟低一个数量级。
4. **声明极其诚实**：反复强调"受控可行性而非生产通用性"，主动列出不覆盖范围（前提抽取、分布式、生产分布、模型重规划质量）。
5. **工程复现度高**：完整 artifact + 独立审计脚本，并披露 OpenAI Codex 辅助编码，报告聚合值可由原始 checkpoint 独立重算。

## 7. 局限与可改进点（个人点评）

- **前提由人写，是最大限制**：所有前提与校验器 developer-authored，未测自然语言前提抽取准确率。ATR 只证明"给定正确前提，闸门工作良好"，而最难的"从 LLM 推理可靠自动抽取可执行前提"被完全跳过——这恰是落地能否成立的关键环节。
- **受控评测信息量有限**：210,000 次执行只覆盖 15 个语义用例，不跑 LLM、非完整 benchmark；100% 安全率相当程度上是"实现符合自己写下的规则"的自我一致性结果。
- **跨资源绑定与依赖遗漏是硬约束**：提交时安全只对 B(e) 覆盖的证据成立；外部策略/预算/授权若目标不检查 token，残余竞态只能暴露给策略层；且依赖遗漏率与误放行率近似线性（0.95%/5.05%/9.97%），说明依赖完备性是安全上限。
- **未测分布式、生产分布与框架集成**：全部单机、进程内计时，0.6 前提/变更的生产外推性未知；仍为独立原型，端到端收益未验证。

## 8. 对我们的启示 / 可借鉴点

### 对 GUI Agent 的可借鉴点（本篇属 Agent 方法论域，非 GUI 落地）

- **选择性再验证 → 长程 GUI 任务的状态漂移检测**：GUI 长程任务同样有"读状态—执行动作"裂缝（早期看到"购物车有货、总价 80、券可用"，很久后才点提交，中间可能页面跳转/价格刷新）。可把"提交订单"的正当性条件记为类型化前提，建立"页面元素→前提→动作"依赖图，局部变化时只沿图重验，输出 KEEP/REFRESH/REPLAN/BLOCK，补上"何时该重规划、何时可继续"的判断层。
- **执行前闸门 + 目标侧绑定 → 不可逆 GUI 操作护栏**：删除、支付、发送、提交表单等适合 PRE_EFFECT 检查 + fail-closed，把 BLOCK 级前提（余额、权限、二次确认）执行前强制重验，且"校验通过"不等于"已执行"。
- **依赖完备性即安全上限 → 元素依赖图保守过近似**：为每个 pending 动作保守链接所有可能影响它的元素/字段，宁可多验、不可漏验。
- **可审计日志与"变化触发检查"**：校验记录证据与校验器版本、解释只增不改；多数变化是 REFRESH/KEEP 级，少数 REPLAN/BLOCK，可显著减少无谓重规划。

### 更一般的方法论启示

- **把"非单调 LLM 推理"与"单调确定性校验"分层**：LLM 提决策与候选前提，确定性校验器提交前把关——这是对抗 LLM 幻觉/漂移的通用护栏思路。
