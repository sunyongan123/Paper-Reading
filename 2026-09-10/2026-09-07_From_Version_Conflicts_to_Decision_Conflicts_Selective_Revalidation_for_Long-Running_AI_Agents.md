## 1. 研究背景与要解决的问题

长时运行 Agent 有一个结构性时间裂缝：**读状态**与**对外执行动作**可能相隔很久，其间支撑该动作的状态完全可能已变。

退款例子贯穿全文：Agent 观察到订单"已送达、有缺陷、未退款、金额 80 英镑"，自身额度上限 100，遂请求退款 80。执行前可能发生五种变化（改名、额度 100→90、缺陷被更正、额度降到 50、同事已退款），**它们都推进版本号，但对"退款是否仍成立"的影响不同**：改名无影响；额度 90 仍满足 80 ≤ 90；额度 50 使前提为假；重复退款使"尚未退款"为假；缺陷被更正则本笔退款不成立、任务仍可行。

乐观并发控制（OCC）只能告诉你"读过的状态变了"，**无法判断该变化是否让待执行动作的正当性失效**；语义可串行化仍属事务判据，但 Agent 跨库推理、长时间暂停，挂起事务不现实。三层各答不同问题：OCC 问"状态变了吗"，ATR 问"变化是否使动作失效"，目标事务/CAS 问"能否原子提交"。核心洞察：**版本变化应是"触发检查"的信号，而非"自动作废决策"的理由**。

## 2. 核心方法 / 思路

ATR 是一套"决策再验证"模型与运行时，位于"观察"与"副作用"之间的窄层。

**形式化。** **前提（Premise）**是决策/动作保持正当所必须为真的条件；**类型化前提**用确定性校验器 `f` 表示、可重复执行。事务 `T = ⟨R, D, I, E⟩` 由读集合、决策、待执行意图、外部副作用构成有向图；**受影响闭包**即图中能到达待执行动作的下游部分，用反向索引定位。

**两种冲突。** 版本冲突 = 资源版本与记录不符；决策冲突 = 当前证据使某个被待执行动作所需、且可达的前提为假或不可验证。四种结果严重度递增：KEEP（保留意图）、REFRESH（刷新展示元数据）、REPLAN（意图不再正当但任务仍可行）、BLOCK（安全/权限/策略/不可逆条件为假、缺失或不可验证，不放行副作用）。

**安全性与流程。** 命题 1：在依赖完备、校验器可靠、token 忠实、观察绑定、目标原子执行五条假设下，被 `B(e)` 覆盖的 BLOCK 级前提为假时副作用无法通过闸门提交；命题 2 给出受影响闭包复杂度 `O(|A_c| + |V_c| + L)`。运行时 `Validate(x, e)` 经反向索引求出可达待执行集合 `C_aff`，对每个必需前提调用校验器并取最高严重度，按绑定策略得结果 `b`，允许则 `conditional_apply(e, b)` 原子提交、被拒则重验。为闭合 time-of-check/time-of-use 竞态，ATR 把校验过的目标版本传入原生事务/CAS/租约；但外部策略/预算/授权的版本未必推进，需强绑定否则记为"未绑定"，不可逆副作用应失败关闭。

## 3. 关键实验结果

实现为 Python 3.11 紧凑运行时：不可变记录、哈希反向索引、类型化校验器、带版本 token 的内存目标；SQLite 测试床用于并发竞态、checkpoint/resume 与跨资源提交。评测三个确定性场景（退款、云修复、采购），每个五种变更（1 KEEP、1 REFRESH、1 REPLAN、2 BLOCK），即 40% 安全、60% 不安全。

**主结果（表 3）：**

| 方法 | 不安全放行率 | 安全却重规划率 | 每次变更前提数 | p50 延迟 |
|---|---|---|---|---|
| NoCheck | 100.0% | 0.0% | — | — |
| VersionAbort | 0.0% | 100.0% | — | — |
| FullScan | 0.0% | 0.0% | 6.0 | 39.9 μs |
| **ATR** | **0.0%** | **0.0%** | **0.6** | **10.8 μs** |

NoCheck 放行 126,000 次无效副作用（占受控变更组合 60.0%）；VersionAbort 未放行任何无效动作，却把全部 84,000 次安全变更重规划；ATR 与 oracle 完全一致（0 误放行、0 误阻断）。总计 7 组打乱种子调度、每工作负载每次 10,000 条轨迹，共 **210,000 次受控执行**（对应 15 个语义变更用例）。

**持久化与成本。** 十个语义单元中，NoCheck 与 VersionAbort 的精确匹配率为 40% 和 20%，FullScan 与 ATR 各 100%；ATR 每次恢复变更平均只评估 **0.6 个类型化前提**，FullScan 需 **6.0 个**。ATR 的 p50/p95/p99 进程内延迟为 **10.8 / 13.0 / 20.5 μs**；无关记录读从 13 增到 4,093 时，ATR 仅从 8.8 变为 **9.3 μs**，FullScan 则从 12.1 暴涨到 **2595.9 μs**（约 280 倍）。

**竞态与失效模式。** 7,000 对两客户端 SQLite 并发更新中每对恰好一个提交。刻意安排的跨资源历史里，仅靠目标侧 CAS 会在策略上限已为假后仍提交 100/100 次，加入被检查的策略 token 后拒绝 100/100 次。随机删除唯一关键依赖边时，1%/5%/10% 遗漏率对应误放行率 0.95%/5.05%/9.97%——**选择性校验只有在依赖捕获完备或保守过近似时才安全**。

## 4. 亮点与贡献（Why it matters）

1. **概念切分干净有用**。"版本冲突 ≠ 决策冲突"点出痛点：要么无视变化（NoCheck，危险），要么一有变化就全盘作废（VersionAbort，浪费）；ATR 给出第三条路。
2. **把"可执行前提"而非"自由文本理由"当作再验证对象**。作者拒绝把思维链当前提，要求前提映射到确定性校验器，模型生成的前提在被映射前视为**不可信**。
3. **同时拿到安全性与选择性**。受控实验中 ATR 误放行与误阻断均为 0，每次变更只评估 0.6 个前提（FullScan 为 6.0），延迟低一个数量级。
4. **诚实到罕见的效果声明**。作者强调这证明的是"受控可行性"而非生产通用性，并明确列出不覆盖范围。
5. **工程完整度高**。提供可复现 artifact（原型、工作负载、checkpoint、CSV、审计脚本），并披露用 OpenAI Codex 辅助编码与图表。

## 5. 局限与可改进点（个人点评）

- **前提由人写，是最大限制**。所有前提与校验器都是 developer-authored，未测量自然语言前提抽取的准确率；ATR 只证明"给定正确前提，闸门工作良好"，**最难的一步（从 LLM 推理自动可靠抽取可执行前提）被跳过**。
- **受控评测语义信息量有限**。210,000 次执行只覆盖 15 个语义变更用例，不跑 LLM、非完整 benchmark，100% 安全率相当程度上是"实现符合自己写下的规则"的结果。
- **跨资源绑定与依赖遗漏是硬约束**。"提交时安全"只对 `B(e)` 覆盖的证据成立，对外部策略/预算/授权，若目标不检查 token，残余竞态只能暴露给策略层；且 1%/5%/10% 遗漏率对应 0.95%/5.05%/9.97% 误放行率（近似线性）。
- **未测分布式、生产分布与框架集成**。全部单机、进程内计时，0.6 前提/变更的生产外推性未知；当前仍是独立原型，端到端收益尚未验证。

## 6. 对我们的启示 / 可借鉴点

### 对 GUI Agent 的可借鉴点

- **选择性再验证 → 长程 GUI 任务的状态漂移与决策失效检测**。GUI 长程任务中"读状态"与"执行动作"同样有裂缝：Agent 早期看到"购物车有商品、总价 80、优惠券可用"，很久之后才点"提交订单"，中间可能有页面跳转、价格刷新等变化。可把"提交订单"的正当性条件（商品仍在购物车、库存 > 0、价格 ≤ 预算等）记为**类型化前提**，建立"页面元素 → 前提 → 动作"依赖图，局部变化时只沿图重验受影响前提，输出 KEEP / REFRESH / REPLAN / BLOCK，补上"何时该重规划、何时可继续"的判断环节。
- **"执行前闸门 + 目标侧绑定" → 不可逆 GUI 操作的护栏**。删除、支付、发送、提交表单等适合套用 PRE_EFFECT 检查与 fail-closed 策略：把 BLOCK 级前提（余额、权限、二次确认）执行前强制重验，且"校验通过"不等于"已执行"。
- **依赖完备性即安全上限 → 元素依赖图的保守过近似**。选择性校验只有在依赖捕获完备或保守过近似时才安全；迁移到 GUI 必须为每个 pending 动作保守链接**所有**可能影响它的元素/字段（宁可多验、不可漏验）。
- **可审计日志与"变化触发检查"**。每次校验记录证据与校验器版本、解释只增不改，便于合规审计与复盘；且 ATR 表明多数变化是 REFRESH/KEEP 级，只有少数是 REPLAN/BLOCK，可减少无谓重规划。

### 更一般的方法论启示

- **把"非单调的 LLM 推理"与"单调的确定性校验"分层**：LLM 提出决策与候选前提，确定性校验器在提交前把关。
- 本文与第 1 篇 Hi-FLoop 形成对照：Hi-FLoop 用"分支持久性"回答"状态变了要不要改计划"，ATR 用"前提再验证"回答更细粒度的版本。

## 7. 延伸阅读

- **CoAgent**——并发 peer 的顺序化与冲突上报。
- **SemIso**——保证 prompt/model/index/policy/tool 在持久化续跑中兼容。
- **Mnemosyne / Cordon / Atomix**——提案准入、释放前组合流校验、投机副作用何时结算。
- **Sagas**——长时程恢复的补偿事务范式，ATR 不解决崩溃恢复与多系统副作用。
- **MCCache**——事务式请求的缓存单调性，与 ATR 的"观察绑定决策与副作用"形成对比。
- **Agentic Transaction（semantic-ACID）**——更宏观的语义 ACID 提案，ATR 自定位为其下方的决策校验层。
