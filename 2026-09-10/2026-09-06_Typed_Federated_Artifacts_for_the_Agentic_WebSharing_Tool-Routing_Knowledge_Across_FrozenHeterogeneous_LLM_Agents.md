# Typed Federated Artifacts for the Agentic Web: Sharing Tool-Routing Knowledge Across Frozen, Heterogeneous LLM Agents

> 提出"类型化联邦构件"作为智能体网络的交换单元，让冻结且异构的 LLM Agent 能共享"该调哪个工具、什么时候不该调"的知识；实验显示收益主要来自类型化格式而非联邦经验，并附两个关于 Agent 评测的负面发现。

## 1. 研究背景与要解决的问题

开放智能体网络里，不同组织各跑着不同厂商的**冻结模型**、历史数据私有，但仍有可互相传授的知识——**该调哪个工具，以及什么时候不该调**。

问题是**没有公认的交换单位**。共享模型更新不行（模型冻结且架构各异），共享原始轨迹会泄露隐私，共享纯文本则让协议"瞎了眼"——无法分辨哪部分是**需裁剪加噪的数值统计**、哪部分是**必须存活于合并的规则**（"该工具永远不要用于 x"）、哪部分是**规范文档**。

作者主张：交换单位应在联邦边界携带**类型签名**——类型化联邦构件是对象 C 配 schema S，S 给每个字段规定角色、类型与校验规则。这样三件在扁平文本上"定义不清"的操作变得 well-defined：**逐字段差分隐私**（敏感度是声明的而非估计的）、**逐字段冲突消解**（分歧按字段保留，而非对整串投票）、**跨模型迁移**（构件在推理时被读取，而非烧进参数）。

## 2. 核心方法 / 思路

**抽象层**是"类型化构件 + 类型化合并算子"：构件只有通过校验才有效（场景、预警、模板须指向已注册工具，数值字段须落在声明范围内），不合法贡献在合并前被拒。**实例化**叫 **SYNAPSE**：每个客户端从自身经验构建 compendium，含 **M** 工具元数据与使用统计、**U** 奏效场景、**P** 什么时候不该用的预警、**T** 调用模板、**A** 结构化附录五部分。

**合并**：每轮先按工具对场景聚类（余弦 ≥ 0.85），再在簇内对 {scenario, precaution, annex} 做**逐字段多数投票**，异议保留为**类型化 conflict_log**，同轮渲染给路由器，最终变成 "do not use when" 条件——这是只有类型化单元才能表达的操作，扁平字符串里没有 precaution 槽位可挂异议。**推理**时路由器用 Jina v2 embedding 检索 top-k = 5 个工具，由冻结 LLM 打分，候选以"描述优先 + when to use + do not use when"字段化呈现；**隐私路径**上 schema 支持对 M 的数值字段裁剪与拉普拉斯加噪（(ε, 0)-DP）及文本字段掩码。

**消融设计**是本文最干净的部分：ROUNDDELAYED（异议延后一轮）、MAJORITY（丢弃异议）、**结构化但无类型**对照（同样字段序列化成一个扁平 JSON，按整串投票）；另把"合并方式"与"呈现方式"正交组合做交叉实验。

## 3. 关键实验结果

**主实验**：StableToolBench，共 **3,180 个工具**（先移除 192 条垃圾，再移除 **1,916 条**与测试查询精确/近似的训练项以避免泄漏）。K = 5 客户端，每客户端 5,000 条经验，3 轮，路由器 Llama-3.1-8B-Instruct。

**联邦几乎无损耗**：SYNAPSE 与 CENTRALIZED 差距**不超过 1.1 个百分点**；真正重要的是"把经验汇到一起"——LOCAL-ONLY 落后 **12~27 点**。相对 DOCS-ONLY，客户端经验在单工具查询上贡献 **4~8 点**；多工具查询少约 2 点，但 oracle 检索下经验在**每个分组**都高 **7~12 点**（0.762 对 0.658），说明那是检索问题而非构件问题。

**类型化 vs 扁平化（核心结论）**：把**同样的字段**序列化成一个字符串，在**注入任何矛盾之前**（0%）就已掉 **8.5 点**（0.583 对 0.497，3 seeds）；注入矛盾后类型化各臂在 60% 时只掉 1~3 点、扁平臂几乎不掉，但由于起点低 8.5 点，60% 时所有类型化臂仍高于扁平臂在 0% 的水平。**交叉实验揭示机制**：类型化合并 + 扁平呈现只有 **0.460**，甚至**低于**扁平合并 + 扁平呈现的 0.497；扁平合并 + 字段标签呈现为 0.531；类型化合并 + 类型化呈现达 0.583。结论明确：**类型的价值必须从合并一路存活到推理**，任何一半单独存在都不起作用。**冲突策略之间则无差别**：保留 conflict log、延后一轮、直接丢弃在每个矛盾率下都在噪声范围内。

**τ-bench retail**（14 工具、55 留出任务、GPT-4o）：PLAIN 0.596，**所有知识库臂至少高 6.7 点**（DOCS-ONLY 0.679、SYNAPSE 0.663、CENTRALIZED 0.672，三者在一个标准差内）。作者据此指出：**增益来自知识库格式，而非联邦经验**。

**两个负面发现**（全文最有价值处）：
- 用 GSM8k 加主题标签做路由代理任务时，TF-IDF+SVM 达 **0.92**，且**把构件随机重标后仍保持 0.82**（它读查询文本而非构件），而 LLM 路由器在四种 prompt 下只有 0.44。这类 benchmark 测的是文本分类，不是路由。
- **ToolBench 指令池包含 StableToolBench 全部测试查询**（精确匹配，过滤后 729/729），分类器在原始池上直接拿到 **1.000**；去重后仍达 **0.817**，比所有 LLM 路由臂高 **26 点**，其中约 **21 点是检索召回**贡献，"unseen"只是相对 ToolLLaMA 训练划分未见。作者放出 overlap filter，并指出该 benchmark 无法考察"路由真正存在的场景"——**一个没有任何标注查询的工具**。

## 4. 亮点与贡献（Why it matters）

1. **抽象选得准**。"在联邦边界携带类型签名、以构件而非模型为交换单位"同时解决了三个原本靠启发式处理的问题。
2. **消融做得干净**。分离"类型 vs 结构"、交叉"合并 vs 呈现"，把收益精确定位到"类型从合并贯穿到推理"，方法论价值高于结果本身。
3. **诚实报告归因**。明确说"federation costs nothing, pooling is what matters"、τ-bench 上增益来自格式而非联邦经验；两个负面发现（主题代理任务实际在奖励分类器、StableToolBench 池内含测试集并给出过滤）对任何做 Agent 评测的人都是直接警告。
5. **负向知识被显式建模**。"什么时候不该用某工具"提升为 schema 一等字段。

## 5. 局限与可改进点（个人点评）

1. **隐私是"声明"而非"测量"**。标题与摘要把联邦隐私当作核心动机，但作者自己写明**所有结果都在关闭噪声下跑的**，全文没有任何 privacy–utility 数字。
2. **跨模型迁移证据不足**。论文明确承认"shown for one 8B reranker"并把跨模型实验列为未测事项，但"跨冻结异构模型共享"恰是标题最核心的卖点。
3. **主结论建立在作者自己承认有缺陷的 benchmark 上**。StableToolBench 被证明池内含测试集且词面可解，Table 1 的主要对比却全在此完成；相对干净的 τ-bench 只有 14 工具、55 任务，统计力极弱，核心结论因此缺少一个干净有力的验证场。
4. **通信成本、联邦设定与 GUI 适用性都未充分验证**。20 MB JSON / client / round 被当作可接受代价提出，却没与替代方案（原始轨迹、扁平文本、adapter）比较收益；K = 5、category-coherent 划分、每客户端 5,000 条经验的设定也相当均匀，真实联邦里客户端高度异质、覆盖不均，LOCAL-ONLY 落后 12~27 点的对比可能被放大。而 GUI Agent 的"路由"是"下一步点哪个控件"，比工具选择更依赖视觉状态与界面上下文，类型化构件是否够用同样未讨论。

## 6. 对我们的启示 / 可借鉴点

1. **"交换构件而不是模型"可迁移到 GUI Agent 多端协同**。不同团队训出的 GUI Agent 可共享"某应用的控件语义、常见陷阱、操作模板、导出流程"这类结构化知识，而不必共享权重（架构可能不同）或原始轨迹（隐私问题）。
2. **schema 化经验库是可直接落地的工程实践**。把知识库设计成有字段角色、类型、范围校验的对象而非自由文本，在本文里换来 8.5 点重排准确率；同时注意"类型必须从合并活到推理"——只在上游结构化、到下游又拍平，收益会全部丢失甚至变负（0.583 → 0.460）。
3. **评测泄漏审计应成为标准动作**。任何以"未见工具/应用/任务"为卖点的 benchmark，都应先检查训练池是否含测试查询；我们用 GUI benchmark 时应照搬 overlap filter 思路自查。
4. **"什么时候不该做"值得显式建模**。GUI Agent 里"这个按钮在当前状态下不该点"往往比"该点哪个"更难学也更值钱（一次误点可能不可逆）；做成独立字段后可直接用于 RL 的动作屏蔽或惩罚设计。报告增益时也应学本文做归因拆解，否则容易把工程收益误报成方法贡献。
5. **对 RL 方向的提醒**：若在多客户端上做 GUI Agent 在线训练，"交换什么"会先于"怎么训练"出现，本文答案是"交换带类型的经验构件"。
