# Selective Knowledge Control for Continual GUI Agent Learning over Application Streams

> 用神经元级梯度手术在应用流上持续训练 GUI Agent：把历史知识分成"该保护的专属知识"和"该继续演化的共享知识"，分别做梯度截断与正交投影，在 OSWorld 八阶段流上把整体成功率平均抬高 6 个百分点以上。

## 1. 研究背景与要解决的问题

GUI Agent 在真实部署中很少面对固定数据分布：新应用不断出现，界面布局在变、工作流是用户特有的、新功能持续引入新任务。于是 agent 天然处于持续学习场景——既要学会新应用，又不能丢掉旧应用的本事。

这与传统持续学习不同。传统方法只权衡**灾难性遗忘**与**快速适应**；而 GUI 应用之间既有大量**共享知识**，也有各自的**专属知识**。论文的例子很直观：在 Calc 里"导出 CSV"和在 GIMP 里"导出图片"，前半段完全一样（打开 File 菜单、选 Export、与导出对话框交互），后半段才分道扬镳（Calc 关心分隔符与编码，GIMP 关心 JPEG 质量与色彩配置）。

真正的难点因此不是"要不要保护历史知识"，而是**分辨哪些该锁死、哪些该继续复用**。已有方法都做不到：参数冻结与重要性正则（如 EWC）把受保护参数一视同仁地约束，连新应用需要的共享知识也一起压住；梯度手术（如 PCGrad）能消除冲突梯度，却分不清"可复用"与"必须保护"；神经元级方法更细，但保护集固定，同样不区分这两类。

## 2. 核心方法 / 思路

设定：单个模型在应用流上顺序微调，第 t 阶段用第 t 个应用的数据微调 π_θt，训完把模型与"历史知识状态"传给下一阶段。核心数据结构是紧凑的历史状态 S_t = (C_hist, U_down, U_gate, U_up)：C_hist 是被保护的 MLP 神经元下标，U 是每个受保护神经元在三个投影上累积的**历史参数更新方向子空间**。存的不是旧模型副本或旧轨迹，而是"哪些神经元重要 + 它们过去往哪动过"。

三步围绕一个关键观察：**一个神经元在当前输入下是否被激活，恰好能区分它是共享的还是专属的**。

**第一步，激活条件前向划分。** 在 MLP down 投影输入上挂 forward hook，统计每个神经元当前 batch 的平均绝对激活值 a_j，用 top-ρ 比例（而非固定阈值）选出高激活集 C_cur；与历史保护集 C_hist 求交得共享集 C_share（历史重要且当前在用），求差得专属集 C_excl（历史重要但当前用不上）。

**第二步，神经元级反向梯度手术。** 对 C_excl 直接把梯度置零——当前应用不用它就不许改，彻底消除干扰；对 C_share 把梯度投影到历史方向子空间的正交补（g̃ = g − U Uᵀg），允许学新东西但只允许在"垂直于过去所有改动方向"的空间里动；其余神经元梯度不变。

**第三步，阶段末状态更新。** 用整阶段累积激活统计重选 top-ρ 神经元并入 C_hist（保护集只扩张）；再把该阶段给受保护神经元带来的参数位移向量、按"该神经元被选中过的所有阶段"堆成矩阵，做截断 SVD 保留 r_svd 个主方向作为新 U。此步只在阶段之间做一次。

与已有方法最本质的差异：**不重放历史轨迹、不算旧应用梯度、不存每应用的完整 checkpoint**，代价只有一次前向 hook 采集与一次反向梯度改写。

## 3. 关键实验结果

实验在 **OSWorld** 上做，基座 **UI-TARS-1.5-7B**，基于开源 DART-GUI 用 GRPO 训练。构造 **8 阶段应用流**：vlc → Thunderbird → libreoffice_writer → libreoffice_impress → LibreOffice Calc → gimp → VSCode → chrome。每阶段训完在所有已见应用上评三次。超参 ρ = 2%、r_svd = 4。

**主结果**：本文方法在 Stage 2 到 8 的每个可比阶段都优于朴素顺序微调，提升在中后期最明显——Stage 3、6、7 整体成功率分别高出 **12.6、7.1、10.6 个百分点**；Stage 8 为 42.7% 对 37.3%（+5.4 点）。

**遗忘与适应的拆解**更有说服力。作者定义 RP（保留性能，惩罚相对历史峰值的下滑）、CP（新应用成功率）、RAH（两者调和平均）。平均下来本文把 **RP 提升 6.3 点、CP 提升 9.1 点、RAH 提升 9.8 点**，两个方向同时涨；Stage 2 的 RP 达 100%（基线 89.3%），Stage 3 的 CP 为 57.1% 对 47.6%。

**与其他持续学习基线对比**（同配置）：Stage 3 整体成功率本文 **50.3%**，Replay 44.0%、EWC 44.8%、LoRA 41.4%（每应用一 adapter + 指令路由）。

**消融**直接验证收益来源：朴素微调 37.6%、静态投影 41.5%、静态冻结 40.1%、本文 **47.1%**。静态冻结与静态投影都明显不如本文，说明关键不在"冻结还是投影"，而在"按当前激活情况分区对待"。

**超参敏感性**：ρ = 1%/3% 掉到 40.9%/44.2%（ρ = 2% 为 50.3%）；r_svd = 2/8 掉到 38.5%/38.7%（r_svd = 4 为 42.7%），两者都是"中等最优"。

**开销**：每步训练 4279.23 秒 → 4324.00 秒，仅 **+1.0%**；token 吞吐 −3.3%，算力吞吐 −1.9%。

**案例**：Stage 7 在 VSCode 学到的"从 VSIX 安装扩展"流程在 Stage 8 的 Chrome 装扩展任务中被成功迁移并完成；基线则在文件选择器状态改变后丢失确认控件，未确认来源即终止而失败。

## 4. 亮点与贡献（Why it matters）

1. **问题定义清晰**。"持续 GUI 学习 ≠ 传统持续学习"这个 framing 本身比方法更有价值，它解释了 EWC 这类方法在 GUI 流上为何失效。
2. **信号选择聪明**。用"当前输入是否激活该神经元"判别共享/专属，不需要额外任务标签、旧任务数据或人工指定通用能力，消融证明它正是收益主因。
3. **工程上真轻**。不做 replay、不算旧梯度、不存多 checkpoint，训练时间仅涨 1.0%，可作为插件叠在现有 RL pipeline 上。
4. **度量有参考价值**。RP/CP/RAH 把"遗忘了"与"没学会"拆开报告，比单一总体成功率更能诊断问题；且整个验证在真实 OSWorld + 8 个桌面应用上端到端完成。

## 5. 局限与可改进点（个人点评）

1. **评测规模偏小，统计力存疑**。只有 8 个应用、一个基座、一个 benchmark，每阶段仅评三次。表格里已见波动：Stage 8 的 RP 反比基线低 2.9 点，Stage 6 的 Thunderbird 也 −2.2 点；作者未报置信区间或显著性检验，"每阶段都更好"的稳健性没有量化。
2. **只管 MLP，没管注意力和视觉编码器**。但 GUI Agent 的核心能力之一是视觉 grounding，视觉侧表征是否更易遗忘、是否更需保护，论文完全没碰。
3. **对超参敏感，且有隐含假设**。ρ = 2% 比 1% 和 3% 高出近 10 点，r_svd = 4 比 2 和 8 高 4 点，换 backbone 或应用流大概率要重调；而用固定比例而非绝对阈值，等于假设每阶段重要神经元占比相近，若某阶段引入大量全新知识就会选错。
4. **应用顺序固定**。顺序消融放在附录，但真实部署中应用到达顺序不可预知，顺序鲁棒性是实用性的关键。
5. **与 LoRA 的对比不够公平**。LoRA 那行用"每应用一 adapter + 指令路由"，路由选错就直接崩，弱可能来自路由器而非 LoRA 本身。
6. **历史状态增长未分析**。C_hist 单调扩张，论文只说状态"compact"，没给随阶段数增长的规模曲线，也没讨论长应用流下保护集饱和会怎样。

## 6. 对我们的启示 / 可借鉴点

1. **梯度手术可做成 RL 之上的轻量插件**。做 GUI Agent 在线/持续训练时，只需 forward hook 采集激活 + 反向后改写梯度，不改优化器、不改数据管线、不需重放 buffer，对已有 GRPO pipeline 侵入性极小。
2. **RP / CP / RAH 值得直接借用**。只报总体成功率就无法判断一次改动是"学会了新任务"还是"忘掉了旧任务"。
3. **"共享 vs 专属"可迁移到 GUI Grounding**。把跨应用通用的视觉定位能力视为共享神经元、App 特有控件语义视为专属神经元，分别用正交投影与截断处理，是一个自然但尚无人做的实验。
4. **消融结论的普适含义**："激活感知"远好于"静态冻结/静态投影"，意味着**"当前输入是否使用某条通路"本身就是判断其可否复用的强信号**，任何做知识隔离、参数高效微调或 MoE 路由的工作都可借鉴。
5. **对 Benchmark 的启发**：应构建**多应用顺序流式评测**并绘制遗忘曲线。当前很多 GUI benchmark 只测"在某应用上能否做对"，无法暴露持续学习能力。
6. **反面提醒**：本文结论全建立在单一 backbone 与固定顺序上，若要引用或复现，应先在第二个 backbone（如 Qwen-VL 系）与随机顺序上验证。
