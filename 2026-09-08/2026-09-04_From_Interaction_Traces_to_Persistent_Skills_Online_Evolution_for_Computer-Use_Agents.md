## 1. 研究背景与要解决的问题

让大模型"用电脑"（computer-use agent）已经在 OSWorld、WebArena 上能做不少真实桌面/网页任务了。但有一个遗憾：它的经验是**转瞬即逝**的——一次跑通的操作流程、一次踩过的坑，任务结束就丢，下次同类任务还得从头摸索，甚至重复同样的失败。已有人尝试给 agent 外挂"技能库"，但两个问题其实没摸清：第一，同样一套系统，挂着会自我更新的技能库，比不带库的对照组多值多少？第二，技能库的长期动态如何——技能真的被跨任务复用了，还是只是任务私房笔记？反复修改某技能就一定能救回它来源的任务吗？作者认为光看"最终分数"回答不了这些问题，于是搭建了可审计的在线技能演化框架，用带来源追踪的纵向实验来回答。

## 2. 核心方法 / 思路

整套系统像给 GUI agent 装了一套"外部硬盘上的程序性记忆"，关键是**把执行与演化彻底分开**。

**冻结快照 + 读执行/写演化**：每一轮（iteration）开始时，把当前技能库导出成只读快照 S_t，本轮所有任务都在这个冻结状态下执行，执行中绝看不到本轮内的技能修改。本轮跑完，轨迹被加工成证据，经过诊断后产生一批"技能变更"（新建/编辑/删除/不改），这些变更只在**下一轮**的快照里才生效。这样"这轮怎么跑的"和"技能怎么变的"彼此隔离，模型参数的微调/退化不会与技能演化混为一谈。

**运行时与技能交互（渐进式检索）**：行动生成（Executor，用 EvoCUA-32B）与 GUI 落点（Grounding，用 MVP）两个模型全程冻结。每轮把技能库里所有技能的"名字+一句话描述"渲染成目录塞进 Executor 的提示词，只有它觉得相关、显式调用 get_skill(name, reasoning) 时，才把某个技能的完整 SKILL.md 正文取回来当工具结果——技能正文不进上下文，检索动作也是只读的。

**轨迹抽象与技能演化（三个 LLM 角色）**：Extractor（Kimi K2.5）把原始轨迹+评估器得分+技能调用遥测整理成结构化事实（任务结果、逐步"状态-动作-效果"、重复模式等），用官方评估器分数压过模型自述；Proposer 基于同一任务最近至多 5 轮的证据历史，输出 create/edit/delete/no-op/unresolved 提案；Coordinator 校验提案（新技能需 5 次观察、名字按域前缀、超尺寸编辑降级），Skill Builder 再把"高层意图"物化成完整可替换的 SKILL.md。每次成功变更单独记一次 Git commit，技能从哪个任务出生、被谁改过、被哪个任务取用过，全部留痕。

**对照实验设计**：Full（技能库可演化）与 Empty（空库对照组，同接口但库恒为空、演化模块禁用）独立纵向跑，共用同一固定 Executor-Grounding、同一任务集与轮次。前 5 轮空库预热，第 5 轮起 Full 才第一次见到非空技能库。

## 3. 关键实验结果

在 OSWorld 的 4 个桌面域（GIMP 26 任务×35 轮、VLC 17×20、LibreOffice Writer 23×20、Thunderbird 15×40）上做配置匹配的纵向对比：

**① Full 的预热后平均分全面领先**：GIMP 80.2 vs 74.4（+5.7 个百分点）、VLC 64.0 vs 45.4（+18.6）、Writer 63.9 vs 52.0（+11.8）、Thunderbird 74.7 vs 62.3（+12.4）。但作者诚实指出：领先既非均匀也非单调——Writer 在双方都还是空库的预热期就已差 +9.1，这部分差距不能归因于技能；GIMP（预热 −4.0）和 Thunderbird（−6.7）都是技能库启用后才由负转正。每条件-域只跑一条独立纵贯轨迹，所以这是描述性结果，不是显著性检验。

**② GIMP 溯源分析显示技能被"共享复用"而非私藏**：35 轮后库里共 27 个技能；82.4% 的有效 rollout 至少调用过一次 get_skill；在全部技能调用中，56.7% 取回的是当前任务自己起源的技能，**43.3% 取回的是别的任务创造的技能**——这是"共享程序性记忆"的直接证据（但取回≠真正照着做，遥测只能证明调用了哪个技能）。

**③ "修订空转"（revision churn）是醒目的失败模式**：背景透明化任务一手创建了 gimp-select-uniform-background、gimp-remove-uniform-background、gimp-add-alpha-channel 一族技能，其中 gimp-add-alpha-channel 被反复接受编辑，但它的起源任务在 35 轮里只成功 2 次（5.7%）。失败证据不断驱动改库，任务却始终没被救回来——指向固定 Executor-Grounding 栈本身存在瓶颈，技能文本修复不了动作生成或落点定位的根本缺陷。

## 4. 亮点与贡献（Why it matters）

1. **罕见的诚实对照**：不是"挂了技能库就涨分"的营销式结论，而是配置匹配的空库对照 + 纵向轨迹，明确区分"哪些提升可能来自技能、哪些预热期就存在"。
2. **不碰模型参数的自适应范式**：技能演化完全发生在外部，对"不能随便重训、部署环境受限"的产品场景很有参考价值。
3. **版本化与可追溯设计**：Git 式提交、快照冻结、来源任务留痕，让"技能库是黑箱"变成可审计对象，也为后续做技能质量治理打了地基。
4. **把失败模式也讲清楚了**：修订空转、域相关收益不稳定、检索不等于遵循——这些负面结论比涨分更有信息量，能防止同行盲目堆技能库。
5. **面向研究问题的评测粒度**：用来源追踪数据回答"跨任务复用是否存在"，而非只看端点分数，方法论值得借鉴。

## 5. 局限与可改进点（个人点评）

- **证据强度偏弱**：每条件-域只有一条独立运行，随机波动无法估计；预热期不平衡（Writer 空库就 +9.1）使"后 5 轮差 = 技能贡献"的因果解读不成立，作者也承认。多副本复跑或至少 Full/Empty 各跑 3~5 条，结论可信度才会质变。
- **任务集是重复固定的**：同域每轮跑同样的任务，衡量的是"背下这套题"的域内适应；对没见过的任务（真正的泛化价值所在）零评测，实际落地收益可能被高估。
- **检索-遵循脱节未闭环**：遥测只记录"调用了哪个技能"，不测"是否照做、是否因此受益"，43.3% 的跨来源复用因此只是观察性证据。作者把"直接测技能遵循度"列为待办，等于承认当前链条缺最后一环。
- **规模与覆盖面小**：GIMP 之外三个域没有技能级剖析；任务数少到 VLC 仅 17 条；串行演化决策顺序依赖、无自动回滚/合并机制，轮次一长库内可能累积互相矛盾的修订。
- **依赖 LLM 评审与抽取的质量**：演化质量完全押在 Extractor/Proposer/Builder 这三个 LLM 角色上，本文没有对"提案被采纳是否正确"做人工抽检，噪声会随轮次滚雪球。

## 6. 对我们的启示 / 可借鉴点

1. **"冻结快照、下一轮生效"是很好的工程纪律**：把"评估看到的状态"与"更新中的状态"隔离，直接消除了我们测试/复评时最常见的脏状态问题——做任何自我改进型 agent 评测都建议抄这个设计。
2. **外挂技能是重训之外的低成本演进通道**：对动辄几十 B 的模型，"技能库 + 固定骨干"能买到相当的增量（本文最多 +18.6 点），产品侧可以先上这个，不必每改一次行为就全量重训。
3. **给技能加"修订刹车"**：修订空转告诉我们，光靠失败驱动改库可能空转；可以实践作者提出的方向——给演化策略加轻量强化信号（下游成功率升了才奖励修订），或设"连续 N 次修订未救回任务即回滚/冻结该技能"的护栏。
4. **复用 CUA-Universe 的混合思路做技能载体**：把技能从纯文本 SKILL.md 升级为"含 CLI 工具面 + GUI 操作 + when_to_use/not_when"的结构化条目，检索命中率和遵循率很可能比纯文本更高。
5. **溯源打点成本低、收益高**：任何轨迹/技能数据管理都应记录"技能出生任务、消费任务、修订历史"，这是回答"数据到底有没有被跨场景复用"的唯一办法。
