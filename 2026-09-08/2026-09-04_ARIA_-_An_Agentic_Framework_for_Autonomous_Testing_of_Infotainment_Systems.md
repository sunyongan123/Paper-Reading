## 1. 研究背景与要解决的问题

现代车载信息娱乐（IVI）系统把导航、媒体、连接、车辆设置等集成在一个复杂平台上，由多团队、多子系统拼装而成，端到端集成验证必不可少；但现状是这类回归测试仍大量靠人工照脚本手点，慢且贵，而 OTA 升级与敏捷迭代让每版都要重跑，人力根本跟不上。脚本化自动化只能部分缓解——测试逻辑一旦写死到内部控件细节，UI 一改就碎。LLM 驱动的 GUI 测试近年兴起，但大多面向 Web/移动 App，且用单/双 Agent 让一个模型同时承担感知、规划、选元素、判定，常把"自己没走对界面"误判成"系统坏了"。

本文要解决的是：在**汽车 IVI 这一工业环境**里，能否用多智能体架构、纯视觉交互，自动执行端到端测试场景——输入直接是一句自然语言（导航路径 + 动作 + 期望结果），让企业现成的手工用例无需改写就能跑起来。

## 2. 核心方法 / 思路

ARIA 是三层架构：顶层 LLM 编排层（模型可插拔，各 Agent 独立会话、消息历史互不可见），中层执行层（闭路流水线、步数限制与重试策略、产物持久化），底层设备接口层（经 Appium + ADB 与被测系统通信，提供 tap/长按/swipe/文本输入等坐标原语，交互后等 3 秒沉降；每步同时采截图与 XML，后者被滤成只含 resource-id/bounds 的紧凑表供查坐标）。

核心是**每步交互都过四个专职 Agent 的闭路流水线**：

1. **Executor（执行者）**：只看当前截图 + 场景描述，刻意不给 XML、内部 API 与文档，像真人用户一样决定下一步高层动作；2. **Translator（翻译器）**：拿高层动作 + 过滤后 XML，映射到具体 UI 元素（resource-id + 动作类型 + 参数），id 无效最多重试 5 次；3. **Inspector（审查员）**：拿目标元素周边截图小块，裁决"该元素语义上是否适合此动作"，不合格就退回 Translator 换选，在交互落到设备前兜住错误映射；4. **Evaluator（评估员）**：动作执行后对比前后截图，做三分判定：Correct（预期变化，继续循环）/ Finished（目标达成，成功）/ Incorrect（疑似缺陷，终止）。主循环外还有 Summarizer，把全程日志整理成结构化报告（OK/BUG/ERROR）与逐步视觉证据。

类比：把一个人肉测试员拆成四人——看屏定计划、找控件、动手前复核、动手后验收，各握所需信息，避免感知判断与缺陷判定互相污染。

框架还有四种执行模式：标准执行（每场景从主屏起跑、BUG/ERROR 自动排队复核）；**短路回放**（跳过前三 Agent 直接重放已录脚本、只跑 Evaluator，用于跨版本低成本回归）；**更强模型复核**（用 claude-opus-4.6 复核初轮 BUG/ERROR 场景）；场景转写（离线把存量手工用例批量转成导航–动作–验证三段式描述）。

## 3. 关键实验结果

工业案例评测在物理台架（Android IVI、脱离整车）上进行，空调子系统被故意禁用作为"已知缺陷"之一。共 30 个场景，覆盖主屏导航、App 启动、搜索、设置、连接开关、状态栏、深层菜单等；默认模型 claude-sonnet-4.6，上限 10 步、5 次翻译重试。

**复核后的主结果**：30 个场景中 28 个跑通完整流水线并给出判定（93.3%），2 个中途执行错误终止；完成的 28 个里 15 个判 OK、13 个判 BUG。与人工真值对照，**20/28（71.4%）判定正确；5 个真实缺陷全部检出（召回 5/5 = 100%、0 漏报）**，但**精度仅 5/13 = 38.5%**，即有 8 个误报，根因一半是 LLM 导航/读图局限、一半是框架不支持的手势与瞬态 UI。

**单 Agent 消融**（同模型、同复核协议）最能说明架构价值：初轮单 Agent 把 23/30（76.7%）判成 BUG、18 个误报，精度仅 21.7%、误报率 72.0%；多 Agent 初轮只判 13 个 BUG、10 个误报，误报率降到 52.6%（它把 8 个不确定场景转成显式 ERROR 而非硬判）。复核后两者最终指标完全收敛（均 28/30、71.4%、38.5%、5/5），差距主要在初轮：单 Agent 常把导航失败误当系统缺陷，且动作轮与判定轮共享对话历史会自我矛盾。**多 Agent 用同样的廉价弱模型就能拿到更可靠的首轮判定**，更少依赖昂贵的复核。

**稳定性与成本**：6 个代表场景各重跑 5 次，3 个完全稳定、2 个 4/5 稳定、最复杂的 Wi-Fi 接入点开关呈 OK1/BUG2/ERR2 高方差；83.3% 单次运行与多数结果一致、80% 与真值一致，**缺陷检出在所有重跑中完全稳定**。成本上，多 Agent 全流程 2,069 次 LLM 调用、约 $139.24（约 $4.64/场景），单场景首轮平均耗时 8.4 分钟（中位 5.2 分钟），符合"夜间回归而非开发期实时反馈"的定位；Translator 是最大成本源（占首轮调用 39.4%），是后续优化首选靶点。

## 4. 亮点与贡献（Why it matters）

- 把 GUI 测试推进到**汽车 IVI 实物环境**，验证多 Agent 闭路架构的工业可行性（93.3% 完成率）。
- 四职责切分 + 信息隔离直接降低首轮误报率（72.0%→52.6%）且无需更强模型，架构与模型的各自贡献被消融区分。
- 纯视觉交互 + 自然语言场景输入，与内部实现解耦、抗 UI 重构、可跨版本复用，且配套存量手工用例的自动转写入口。
- 工程透明度高：逐 Agent 成本分解、token/调用/时延记账、根因分类，对要做落地决策的团队很实用。
- 产出"结构化报告 + 可重放脚本 + 视觉证据"，短路回放模式为接入 CI 回归指出低成本路径。

## 5. 局限与可改进点（个人点评）

- **评测规模小、强结论需打折**：30 场景、仅 5 个真实缺陷，"5/5 召回"是小样本满分，0 漏报不能外推；跨版本回归能力作者也承认未评测。
- **38.5% 精度是落地最大障碍**：13 个 BUG 判定里 8 个是误报，会淹没信号、消耗人工逐条排查；根因明确指向 Evaluator 缺少"期望行为上下文"——论文自曝的第一可改点，却未给实验验证。
- **成本与延迟偏高**：$4.64/场景、8.4 分钟/场景、每步 4 次外部 LLM 往返，多模态 prompt 每步重发是大头；未讨论本地模型/缓存/批处理的降本方案。
- 手势原语少，长按拖拽、瞬态 UI 无法测；Translator 依赖厂商给的 resource-id→描述参考文件，对完全黑盒系统适配存疑；真值由单审阅者判定；开源/本地权重模型未纳入选型。

## 6. 对我们的启示 / 可借鉴点

- **四 Agent 分工可作为 GUI Agent 生产化的"防幻觉"模板**：尤其 Evaluator 只看动作前后屏态、不看导航历史，与我们的 grounding/reflection 解耦思路直接相关——判定者信息越少越干净，越不易被自己的探索历史带偏。
- **把不确定转成显式 ERROR 而非硬判**值得推广：多 Agent 初轮的 8 个 abort 恰是单 Agent 里最易变误报的场景；对应到我们的 Agent，即允许模型说"没把握/需澄清"，并把失败显式化以利于人工 triage。
- **按 Agent 记账（调用/成本）**是好习惯（Translator 占 39.4% 调用、成本大头在复核 pass），可移植进我们的评测 harness，量化"架构优化 vs 换模型"的性价比。
- 短路回放 ≈ 低成本回归，可类比 GUI Agent 的技能缓存/固定流程重放；"误报主导而非漏报"再次提醒评测终点设计值得单独立项（给判定器补充期望状态清单等系统先验），这与 RL 中用系统先验设计 reward 同理。
